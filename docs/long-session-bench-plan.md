# 장기 세션 효율 테스트 계획

- 상태: 계획만, 미실행 (작성일 2026-11-01)
- 관련: 짧은 핑퐁 게임 테스트(3프롬프트, 2회) 결과는 `README.md`의 "효율 테스트 (핑퐁 게임)" 참고

## 목표

긴 세션(프롬프트 약 25개 연속)에서 chaude 하네스가 plain Opus보다 누적 비용 증가가 완만함을 확인합니다. 짧은 세션의 비용 절감(-42.7%)이 긴 세션에서도 유지되는지, 그리고 컨텍스트 회전(rotation)이 비용 곡선을 어떻게 바꾸는지 봅니다.

## 방법

- 같은 프로젝트: 하나의 빈 프로젝트 폴더를 기준으로 두 방식에 같은 시작 상태를 줍니다.
- 프롬프트: 약 25개를 순서대로 보냅니다. 사용자가 평소 쓰는 반말 섞인 구어체로 작성하고, 앞 프롬프트의 결과를 이어받는 후속 요청 위주로 구성합니다.
- 비교군:
  - plain: 하네스 없이 Opus 단독 (`claude` 직접 실행, CLAUDE.md·.claude 없음)
  - harness: chaude 하네스 (Opus main + haiku 서브에이전트)
- 공통 조건:
  - 같은 `effortLevel` 값을 두 방식에 지정 (harness 설정 값과 맞춤, 현재 medium)
  - 같은 permission mode, Bash 허용을 두 방식 모두에 적용 (이전 테스트에서 plain은 Bash가 거부된 적이 있어 반드시 확인)
  - `CLAUDE_CONFIG_DIR`을 실행마다 격리된 빈 폴더로 지정 (전역 설정·캐시 오염 방지)
- 반복: 방식별 3회씩 실행합니다. 실행 사이 캐시 상태 차이를 줄이기 위해 실행 순서를 번갈아 바꿉니다.

## 기록 항목

프롬프트 번호마다 아래를 기록합니다.

- 누적 비용 (USD, 프롬프트 1부터 해당 번호까지 합)
- Opus 토큰 (input, output, cache read, cache create)
- Haiku 토큰 (harness만, 서브에이전트 합계)
- 메인 컨텍스트 크기 (토큰, 프롬프트 시점 기준)
- 회전 횟수와 회전 시점 (harness만, 핸드오프 생성 포함)
- 턴 수, 소요 시간

집계 단위: 실행별 프롬프트 누적 곡선을 만들고, 3회 평균과 범위(최소~최대)를 함께 기록합니다.

## 기대

- plain: 누적 비용이 프롬프트 수보다 빠르게 증가합니다 (초과 선형). 컨텍스트가 커질수록 매 턴 cache read가 늘어나기 때문입니다.
- harness: 컨텍스트 회전으로 메인 컨텍스트가 상한에 묶이므로 누적 비용이 대략 선형에 가깝게 증가합니다.
- 판정 기준(사전 정의): 25번째 프롬프트 시점 누적 비용 비율(harness / plain)과 곡선 형태를 함께 봅니다. 기대와 다르면 그대로 기록합니다.

## 주의점 (caveat)

- Haiku 콜드 재독: 서브에이전트는 매번 새 컨텍스트로 시작하므로 프로젝트 파일을 다시 읽습니다. 짧은 세션에서는 이 비용이 크고, 긴 세션에서 상쇄되는지 확인이 필요합니다.
- 회전 핸드오프 비용: 회전할 때 핸드오프 스냅샷 생성과 새 세션의 재독 비용이 듭니다. 회전 시점별로 따로 집계합니다.
- 캐시 상태: cache read가 비용을 지배합니다. 실행 순서와 간격에 따라 캐시 적중이 달라지므로 간격을 고정하고 기록합니다.
- effortLevel: harness 쪽 설정이 낮은 effort였다면 품질 차이가 있을 수 있습니다. 결과 품질은 이번 계획에서 측정하지 않습니다.
- 표본: 3회는 여전히 작습니다. 범위를 함께 보고하고 일반화하지 않습니다.
- 권한 모드: plain에서 Bash가 막히면 작업 조건이 달라집니다. 실행 전 권한 거부 기록(permission_denials)을 확인합니다.

## 실행 순서 (예정)

1. 프롬프트 25개 목록과 실행 스크립트 작성 (실행 전 검토)
2. 격리된 CLAUDE_CONFIG_DIR 두 세트 준비, 설정 검증
3. plain 3회, harness 3회를 번갈아 실행, 프롬프트별 결과 저장
4. 누적 곡선과 집계 작성, README의 효율 테스트 섹션에 결과 반영

지금은 실행하지 않습니다.
