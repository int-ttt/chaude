## 개선점

1. 조건 B가 변수 2개(입력 압축 + caveman 출력)를 동시에 바꿈 -> 조건 C(원 입력 그대로 + caveman 출력, 번역 포함) 추가하거나, 최소한 차이를 압축/caveman 중 어디 탓인지 구분하는 기록 항목을 둘 것.
   근거: 지금 설계로는 근거 누락·결론 차이가 압축 단계 탓인지 caveman 단계 탓인지 귀속 불가.

2. Opus 출력 토큰을 thinking(추론) 토큰과 가시 출력 토큰으로 나눠 기록할 것. Opus 입력 토큰(cache_read / cache_creation / 일반 입력 분리)도 지표에 추가.
   근거: caveman은 가시 출력만 줄이고 과금되는 thinking 토큰은 거의 그대로일 수 있어, 합산만 보면 절감 효과가 과대·과소 평가됨.

3. 조건 A에도 메인 Haiku의 사용자 전달(요약·중계) 토큰을 측정하고, 순비용 = B 번역 토큰 - A 중계 토큰으로 정의할 것.
   근거: A도 메인 Haiku가 결과를 사용자에게 옮기므로, B의 번역 비용 전체를 추가 비용으로 잡으면 B가 불리하게 계산됨.

4. 메인 Haiku 번역 토큰 측정 방법을 명시할 것 (예: 번역 턴 직전·직후 notes/metrics/2026-10-30.jsonl 누적치 차분, 해당 턴 ID 기록).
   근거: constraint상 번역은 에이전트 호출이 아니라 메인 세션 안에서 일어나므로 에이전트 usage 수치가 없고 다른 턴 토큰과 섞임.

5. 5절 4단계 "Haiku 에이전트로 조건 A/B 실행"을 "메인 Haiku가 직접 압축·번역, opus-architect만 에이전트 호출"로 고칠 것.
   근거: 1절 constraint(번역 = 메인 Haiku 직접 수행)와 모순되어 실행자가 번역을 별도 에이전트에 위임할 위험.

6. 1회 실행 한계 보완: 실행 전에 판정 임계값을 고정할 것 (예: Opus 총 출력 토큰 절감 >= X%, 근거 누락 0건, 결론 불일치 0건일 때만 "유망"). 가능하면 조건 A를 2회 실행해 A1-A2 차이를 잡음 기준선으로 삼고, A-B 차이가 이 기준선 이하이면 "판단 불가"로 기록.
   근거: Opus 출력 길이·내용은 실행마다 흔들려, 1회 차이가 caveman 효과인지 무작위 변동인지 구분할 기준이 없음.

7. "근거 항목" 단위를 정의할 것: 파일 경로, 행 번호, 수치, 명명된 출처, 인용 1개 = 1항목. 판정자가 B를 보기 전에 A에서 근거 목록을 먼저 추출하고, B에만 있는 근거(역방향)도 함께 집계.
   근거: 단위가 없으면 누락 수가 판정자 재량이 되고, A를 정답으로만 쓰면 B가 추가한 근거·A의 누락은 안 보임.

8. "결론 일치" 대상(최종 결정/권고 문장 1개)과 "단가 가중 총비용" 공식(단가 출처 notes/research/billing.md, 모델별 입력·출력·cache read·cache write 단가 x 토큰)을 계획서에 명시할 것.
   근거: 결론이 여러 개인 출력에서 무엇을 비교할지, 어떤 단가표를 쓸지 모호하면 결과 해석이 실행자마다 달라짐.

9. 판정 블라인드화: sonnet-reviewer에게 A/B 대신 X/Y 무작위 라벨로 최종본을 주고, 조건 매핑은 판정 후 공개.
   근거: 판정자가 어느 쪽이 caveman 릴레이인지 알면 루브릭 판정(특히 뉘앙스·결론 일치)에 편향이 생김.

10. caveman 출력 형식을 고정 스키마로 지정해 번역 단계 근거 손실을 막을 것: 근거마다 ID(E1, E2 ...)와 `E1: 경로:행 / 수치`, 주장마다 확신 태그(확실/추정/불확실) 부착. 번역본은 모든 E-ID와 확신 태그를 유지해야 함.
    근거: 자유 형식 caveman은 조사·접속어와 함께 조건문(~라면, ~일 수 있음)도 떨어져 risk_2(뉘앙스)·risk_4(오역)가 커짐.

11. 번역 후 기계 검증 단계 추가: haiku-checker가 caveman 원문의 E-ID·파일 경로·수치·확신 태그가 번역본에 모두 있는지 문자열 대조하고 누락 목록을 기록. caveman 원문과 압축 입력도 notes/runs/에 그대로 저장.
    근거: 근거 누락을 루브릭(사람식 판단)에만 맡기면 놓치기 쉽고, 원문이 남아 있어야 어느 단계에서 빠졌는지 추적 가능.

12. 압축 단계 검증 추가: 압축 입력을 원 입력과 대조해 빠진 사실·제약·경로를 기록 (판정자 또는 haiku-checker).
    근거: compress_rule이 수식어 제거 기준을 판단에 맡겨, 압축 자체가 첫 번째 근거 손실 지점인데 현재 지표에 없음.

13. 프롬프트 캐시 영향 통제: 두 조건을 각각 새 세션(또는 캐시 만료 후)에서 실행하거나, 실행 순서와 cache_read 수치를 함께 기록.
    근거: 두 번째로 실행한 조건이 같은 입력 파일에서 캐시 이득을 받아 입력 비용이 낮게 측정될 수 있음.

14. caveman 준수 여부 지표 추가 (예: 출력 중 key: value/명사구 줄 비율, 인사·접속어 문장 수). 준수 미달이면 결과를 "스타일 미적용"으로 표시.
    근거: Opus가 caveman 지시를 일부만 따르면 절감 실패를 구조 탓으로 잘못 결론낼 수 있음.

15. risk_3의 "설명 규칙"을 구체 체크리스트로 적을 것 (어느 문서의 어떤 규칙인지: 예 CLAUDE.md의 사용자 대상 설명 규칙 항목 나열).
    근거: 규칙 출처·항목이 없으면 루브릭의 "위반 건수"를 판정자가 셀 기준이 없음.

16. 과제 선정 기준 보강: 정답 확인이 가능한 사실(파일 내용, 수치)을 포함하고, notes/에 이미 답이 정리되어 있지 않은 과제로 고를 것.
    근거: 확인 가능한 사실이 없으면 환각/오역 판정이 불가하고, 기존 노트에 답이 있으면 두 조건 모두 복사만 해 차이가 안 드러남.
