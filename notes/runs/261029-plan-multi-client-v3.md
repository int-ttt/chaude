## 4. 라우팅(배정)
- 세션 전환이 아니라 배정. 디스패처가 (target, model) -> 클라이언트를 매핑하고 분류자는 id를 고르지 않는다.
- 분류자 출력: topic/size/kind/worker/task + `model: haiku|sonnet|opus` + `target: design|exec` (kind=설계/판단/반복 실패/'opus로' 설계 요청 -> design, 그 외 exec). 강제 --model 우선, 누락 시 size/kind로 대체.
- 분류자 입력: 새 프롬프트 + 클라이언트 표 한 줄씩 {id, model, topic, ctx, lastUsed, busy} (~3k). 표는 결정론적으로 디스패처가 소유.
- dispatch 블록(자식 입력 맨 앞, 한 블록):
  `[dispatch] id: <route-id>` / `target: design|exec` / `task: <사용자 프롬프트 원문>` / `design: <절대경로|none>` / `result: <디스패처가 지정한 절대경로>` / `classifier: <한 줄 요약>`
  이유: 분류자 task는 요약이라 세부가 빠짐. 결과 경로를 미리 정해야 폴링 가능(6절).
- 설계 파일 조회: 레지스트리 `topic -> 설계 파일 경로`(설계 클라이언트가 저장할 때 디스패처가 기록, route-log). target=exec, size 큼, 설계 파일 없음 -> 먼저 설계 클라이언트로 보내고, 파일 생성(존재+size>0+2초 안정) 후 exec 배정. 비싼 오분류 방향 차단. 파일 없고 소작업이면 "설계 파일 없음"+작업 한 줄 (가정, 검증: 오분류 요약).
- 재사용 규칙(모델별): 따뜻한 클라이언트가 있으면 새로 열지 않는다. 임계값 sonnet/opus ctx < 240k(가정), haiku ctx < 60k(가정; 현재 단일 240k는 haiku에 해당 없음). 검증: route-log 재사용률, 임계 근처 재배정 건수. 바쁜 대상은 그 클라이언트 inbox에 FIFO로 쌓고(다음 턴 전달) Q4 허용 전엔 중복 생성 안 함. 같은 모델 여럿이면 같은 topic/files, 그다음 최근 lastUsed.
- 후속("이어서", "그걸로", 같은 topic)과 맞장구/슬래시는 분류 없이 직전 클라이언트로. "직전" = 사용자가 마지막으로 본 답변을 낸 클라이언트(마지막 디스패치 아님). 가정.
- 시작 절차: 프로젝트 cwd에서 `claude --model X`, env CLAUDE_CODE_PROMPT_CACHE_TTL=1h, 모델별 임계값, 첫 입력 = dispatch 블록(새 실행 클라이언트는 핸드오프 불필요). 기동 실패/중단 -> 표에 dead 표시, 같은 블록 1회 재배정 후 보고.
- 매 프롬프트 분류 재도출(per-prompt 분석 8.5만 = 새 세션 C0 쓰기 6만 + 핸드오프 2.5만 + 기존 400k 캐시 손실): 따뜻한 클라이언트로 배정하면 추가 비용 0, 타 클라이언트 캐시 손실 없음. 콜드 스타트는 C0 쓰기(~6만)만, 핸드오프 2.5만은 사라짐(brief = 설계 파일 경로, 수 k 입력). 남는 비용: (1) 콜드 스타트, (2) 후속이 다른 클라이언트로 갈 때 컨텍스트 손실(파일 재읽기), (3) 한 번 쓰고 다시 안 읽힌 유휴 캐시, (4) 여러 클라이언트가 같은 설계 파일을 각각 읽는 중복 캐시 쓰기(위험). 결론(추정): 분류는 프롬프트마다 유지(호출은 메인의 수 % 이하, 가정, 검증: metrics classify stage 비율), 단 재사용 우선 + 모델당 1개 기본. 새 판단 기준 = 시간당 새로 여는 클라이언트 수. 추가 지표: clients opened/hour, 콜드 스타트 C0 토큰, 재사용 없이 종료된 클라이언트(낭비 쓰기).

## 5. 유지·종료
- 클라이언트마다 따로 적용(캐시가 따로). 타이머 기준 = 그 클라이언트의 마지막 메인 API 요청 시각(DECISIONS:23; 서브에이전트 호출은 메인 캐시를 갱신하지 않음. 가정, 검증: usage 로그). 모든 자식은 TTL=1h로 기동.
- Opus의 keep/end는 호출이 아니라 미리 기록한 의도: 설계 클라이언트가 평소 설계 턴에 설계 파일 `## clients`에 `<client-id|model+topic>: keep | end-after-result`를 적는다. 59:59(3599초)에 하네스가 이 의도를 추가 Opus 호출 없이 그대로 실행. 의도 없음 -> 종료. 정정 3(Opus 판단)과 DECISIONS:23(결정론 59:59)을 합친 [해석]이며 Q2에서 확인. 마진 3570초 적용 여부는 가정(검증: 요청 지연 p95).
- "keep"의 의미: 1시간 안 유휴는 비용 0이라 일찍 끝내도 절약 없음(슬롯만 비움). 1시간 뒤 선택지: 핸드오프+종료(~0.1x ctx+출력), 핑(과금 미확인, 보류), 캐시 만료 후 프로세스 유지(재사용 시 전체 2x 재작성). 핑 없이 keep은 ctx 작을 때(< 약 60k, v2 값, 가정)만 의미. keep/end 판단이 중요해지는 경우는 핑 허용 후와 슬롯 상한(Q4)뿐이므로 과대평가 금지.
- 종료 방식: 실행 클라이언트 = 결정론 스냅샷(토큰 0: 설계 경로+결과 경로+route id+inbox 잔여), LLM 핸드오프 없음(출력이 이미 결과 파일에 있음). LLM 따뜻한 핸드오프는 설계 클라이언트만. 유휴 시간당 N x (0.1x ctx + 5k 출력) 제거.
- 위험(overage): overage/API key에서는 TTL이 5분이고 290초로 폴백한다(DECISIONS:23). 클라이언트별 usage.cache_creation으로 감지. 동시 클라이언트가 구독 한도를 빨리 소진해 폴백 가능성이 커진다. ratestatus가 한도 근접/overage를 보이면 설계 + 실행 1개로 줄이고 290초 사용. 폴백 시 모든 규칙이 클라이언트별로 달라짐.
- 종료 시 백그라운드 에이전트가 있으면 draining 후 종료 (DECISIONS:18). max-drain 3은 chaude 프로세스 전체 공유이므로 명시하거나 클라이언트별로 분리.
- Q3: 59:59 이후 설계 클라이언트를 계속 둘지(live) 스냅샷 후 지연 재시작할지는 사용자 결정.

## 6. 데이터 흐름
- 설계 파일(`notes/runs/<YYMMDD>-plan-<topic>.md`)이 공유 상태. 필수 절 `## evidence`, `## brief`, 제안 `## decisions`, `## open`, `## clients`.
- 설계 클라이언트가 파일 저장 -> 실행 클라이언트는 경로를 받아 읽고 시작. 설계 클라이언트 컨텍스트를 직접 가져가지 않음(정정 6). 결과는 notes/runs/에 파일, 요약만 알림 (DECISIONS:36).
- 메시지는 알림에만. 데이터는 파일에. 송신자는 응답을 기다리지 않고 파일 상태(존재+size>0+2초 안정)로 완료 확인.
- 설계 클라이언트에는 이벤트마다 메시지하지 않는다(읽을 때마다 Opus 턴). 디스패처가 clients.json을 관리하고 다음 설계 턴 입력 앞에 요약만 붙인다: `[clients] +sonnet-1 opened topic X / result Y done / haiku-1 ended`. 에이전트 알림과 같은 패턴(DECISIONS:18, 자동 턴 없음).
- 파일 소유자: 설계 파일=설계 클라이언트, 결과 파일=해당 실행 클라이언트, route-log/metrics=하네스(가정, 검증: 쓰기 경로 코드 확인). 동시 쓰기 기본값: 파일당 작성자 1명 + repo/worktree당 편집 권한 실행 클라이언트 1개, 두 번째는 git worktree 또는 대기(Q5 기본안).

## 8. 오분류 처리
- 오분류 프롬프트는 설계 맥락 없는 클라이언트에 도착하므로 모든 배정에 설계 파일 경로를 포함(4절 블록). 신호: 사용자 모델 강제/재실행, 반복 실패. 재배정은 새 배정이며 컨텍스트는 이어지지 않고 설계/결과 파일로만 이어짐.
- 방향별 비용: 설계가 필요한 일을 작은 일로 본 경우가 더 비쌈(4절 설계 파일 선행 규칙이 차단). 반대 방향은 단가 손해뿐.
- 오분류 요약(모델별 건수, 강제/재실행 목록)은 설계 턴에만 전달. 샘플링으로 오분류율을 쌓은 뒤 조정(가정, 검증: 요약의 오분류율 추이).
