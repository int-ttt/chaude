# caveman 구조 계획서(v4) 설명과 사용자 결정 항목

대상: plan/caveman-structure.md (210행). 읽기 전용으로 정리했으며 파일은 수정하지 않았습니다.

## 1. 전체 구조와 핵심 주장

계획서는 구현이 아니라 설계안입니다. 하네스 내부 메시지를 두 채널로 나누자는 주장입니다. 사람이 읽지 않는 에이전트 간 브리프와 반환은 형식이 고정된 축약("caveman")으로 쓰고, 사용자에게 가는 글만 한국어 존댓말로 둡니다.

- 0절 (이전 결과의 제약): 자유 축약은 한정어("만", "제외", "미확인")와 검색 범위, 잘림 여부를 먼저 잃기 때문에 채택하지 않습니다. 형식이 고정된 스키마만 검토합니다. 번역 전용 단계는 추가하지 않습니다. 서브에이전트는 부모 맥락을 상속하지 않으므로 브리프에 맥락을 직접 적어야 합니다. CLAUDE.md 4행의 "Korean, 존댓말."이 서브에이전트에도 적용되어 에이전트 파일만 바꾸면 규칙이 충돌합니다. 차단형 훅은 실행 중 세션을 막을 수 있어 금지하고, 구현은 별도 worktree에서만 합니다. 비용 근거는 1회 측정뿐이라 절감량은 미확인입니다.
- 1절 (목표): 에이전트 간 hop을 형식 고정 축약으로 통일하되 근거(경로:행), 한정어, 검색 범위, 잘림 여부는 필드로 보존합니다. 기존 에이전트 체계, 모델 고정, 메인 스레드 가드는 유지합니다.
- 2절 (3층 채널): L0 사용자와 메인(한국어 자연문), L1 메인과 opus/sonnet(브리프와 결정 반환), L2 opus/sonnet과 haiku(브리프와 읽기/쓰기 반환). 반환 하나에 caveman 본문과 한국어 요약(summary_ko 1~5줄)을 함께 두고, 메인은 summary_ko만 사용자에게 전달합니다. 중계 단계 수는 늘리지 않습니다.
- 3절 (형식): 브리프는 task, paths, ctx, limits, return, lang. 읽기 반환은 claim(경로:행 | 사실 [확실/추정/불확실]), searched, not_found, not_checked, truncated, omitted. 쓰기 반환은 changed, diffstat, check, ws. 결정 반환은 decision, why, rejected, risks, open_q, plan_path. 모든 반환 앞에 status(done/partial/fail/blocked)와 reason 2줄을 붙입니다. 한정어 삭제, 경로 생략, 확실도 삭제는 금지입니다.
- 4절 (에이전트별 적용표): 메인은 B형식으로 내고, opus/sonnet/haiku는 역할별 반환 형식을 씁니다. haiku-extractor는 변경 없음입니다.
- 5절 (규칙 충돌 해소): O1 CLAUDE.md 4행 범위를 사용자 노출 텍스트로 한정, O2 scout/researcher 파일에 예외 1줄 추가, O3 브리프 lang 필드로 호출마다 지정. 계획의 선택은 1단계 O2, 사용자 승인 시 마지막 단계에서 O1로 통합입니다.
- 6절 (형식 감시): 신규 훅 caveman-format.py를 두되 차단하지 않습니다. 모드는 log(기본), warn, off. 필수 키 누락만 검사하고 한정어 손실은 정적 검사로 못 잡는다고 명시합니다.
- 7절 (라우팅): [ws:<id>] 표기와 세션 재개는 메인/하네스 책임입니다.
- 8절 (적용 단계): S0 정본 문서, S1 읽기 경로(scout, researcher)와 감시 log 등록, S2 쓰기 경로, S3 지휘 경로, S4 감시 확대, S5 통합(CLAUDE.md 범위 한정). 단계마다 별도 worktree 브랜치와 커밋으로 되돌리기 가능하게 합니다.
- 9~11절: 바꾸지 않는 것, 정합성 확인 항목, 위험 6건(R1~R6).

## 2. 12장: 사용자만 답할 수 있는 질문

### Q1. CLAUDE.md 4행 범위 한정(O1)을 승인하시는지
- 왜 사용자 결정인가: CLAUDE.md는 전역 규칙이고 변경에는 사용자 승인이 필요합니다. 에이전트가 스스로 바꿀 수 없습니다.
- 선택지:
  - 승인(O1): 4행을 "사용자에게 보이는 텍스트"로 한정하고 에이전트 간 반환은 caveman으로 명시. 장점은 단일 출처와 일관성, 단점은 전역 규칙 변경입니다. S5 단계에서 O2 예외줄을 제거합니다.
  - 미승인: O2(scout/researcher 파일 예외 1줄)로 유지. 변경 범위가 작고 되돌리기 쉽지만 CLAUDE.md와 충돌 상태가 남고 읽기 경로에만 적용됩니다.
  - O3(브리프 lang 필드만 사용): 파일 변경은 없으나 매 브리프 비용이 들고 누락 시 한국어로 돌아갑니다.
- 계획의 기본값: 1단계는 O2, 승인 시 마지막에 O1.

### Q2. haiku-prompter의 TUI 라운드 로그를 L0(한국어)로 볼지
- 왜 사용자 결정인가: 사용자가 직접 화면에서 읽는 로그의 언어이기 때문에 취향과 가독성 문제입니다. 계획표에도 "L0인지 미정"으로 남아 있습니다.
- 선택지: (a) 한국어 존댓말 L0로 표시, (b) caveman 형식 그대로 표시. 사용자가 읽는다면 L0 원칙상 (a)가 자연스럽지만, 결정은 사용자 몫입니다.

### Q3. worktree 기준점에 현재 master의 미커밋 변경을 포함할지
- 왜 사용자 결정인가: 현재 master에는 수정 파일이 많이 미커밋 상태입니다. 단계별 구현은 별도 worktree에서 하고 stash는 금지되어 있어, 기준점을 정해야 합니다. 어느 변경을 살릴지는 사용자의 작업 의도에 달려 있습니다.
- 선택지: (a) 미커밋 변경을 먼저 커밋한 뒤 그 커밋을 기준으로 시작(변경 포함), (b) 마지막 커밋(HEAD) 기준으로 시작(미커밋 변경 제외, 깨끗하지만 현재 하네스 수정과 어긋날 수 있음).

## 3. 13장: 미확인 항목
13장은 사용자 질문이 아니라 아직 확인되지 않은 사실 목록입니다. 일부는 사용자 판단이 개입할 수 있어 함께 적습니다.

1. 본 구조의 토큰·비용 절감량: 비용 근거가 조건 A 1회뿐(총 0.5437달러)이고 B·C는 미실행입니다. 사용자 결정 포인트: 측정을 먼저 할지(측정 선행 게이트) 아니면 형식 도입을 먼저 할지입니다. 계획 문서는 이 선택을 정하지 않았습니다.
2. 모델별 단가: billing.md에 기재가 없습니다. 사용자가 단가를 제공하거나 조사를 지시해야 비용 계산이 가능합니다. 조사 지시는 선택지입니다.
3. 반환 검사용 PostToolUse matcher 이름: 감시 훅을 어떤 도구 이름에 걸지 미확인입니다. 사용자가 아니라 구현 단계의 확인 사항이지만 훅 등록 전에 해결해야 합니다.
4. mode f 기본 활성 여부: 기본 실행에서 live 자식이 켜지는지 미확인입니다. 이에 따라 ws 필드를 none 허용으로 둔 상태입니다. 사용자가 실제 사용 방식(--clients-file 설정 여부)을 알려주시면 확정할 수 있습니다.
5. 서브에이전트 캐시가 부모와 공유되는지: 미확인입니다. 절감 계산의 전제라서 측정이 필요합니다.

## 4. 본문에 흩어진 다른 사용자 결정·확인 필요 항목
- 5절 choice: 1단계를 O2로 시작하는 순서 자체가 계획의 제안입니다. 사용자가 O1 먼저 또는 O3를 원하시면 바꿔야 합니다(Q1과 연동).
- 6절 감시 모드: 기본 log를 쓸지, warn으로 올릴지, 어느 단계에서 올릴지는 사용자 판단이 필요합니다. 차단 모드는 계획에서 제외했습니다.
- 6절 검사 항목: lang: ko 브리프의 summary_ko 존재 검사는 훅이 브리프 본문을 볼 수 있는지 미확인이라 구현 가능 여부가 불명확합니다.
- 6절 훅 이름: caveman-format.py는 제안 이름이라 변경 가능합니다.
- 8절 S5: 통합 단계는 Q1 승인에 종속됩니다. 승인이 없으면 O2 예외 2파일이 영구히 남습니다.
- 8절 적용 자체: "설계 순서이며 실행 아님"이라 실제 착수 시점과 단계별 범위(S1만 먼저 등)는 사용자 승인이 필요합니다.
- 11절 R1·R6: 짧은 작업에서 반환이 길어질 위험과 메인이 브리프를 잘못 쓸 위험은 완화책(빈 값 "-" 허용, 필수 5키)을 쓰지만, 이 트레이드오프를 받아들일지는 사용자 판단입니다.

## 5. 근거와 한계
- 근거: 계획서 원문 전체(1~210행)를 읽었습니다.
- 확인하지 못한 것: 계획서가 인용한 다른 파일(notes/runs/*, flow.md 등)은 열어 보지 않았습니다. 인용 내용의 정확성은 검증하지 않았습니다.
- 4절의 "사용자 결정 포인트" 중 12·13장 외 항목은 제 해석이며 계획서가 명시한 질문이 아닙니다.
