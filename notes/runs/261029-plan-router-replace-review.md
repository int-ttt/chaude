# review: 261029-plan-router-replace.md
verdict: 구조는 타당하나 게이트 정의가 haiku-policy 계획과 어긋나고 선행 구현 단계가 빠져 있어 수정 필요.
evidence: replace plan, haiku-policy plan (rev2) 직접 대조. DECISIONS.md는 grep(router/gate/rollback)만 확인했고 [conductor] 32행의 sonnet classifier 문구는 grep에 안 잡혀 미확인(정책 계획의 인용을 따름).

1. (S0 신설, S1 대체) CHAUDE_ROUTER_MODEL 구현 단계를 S2 앞에 넣는다. 이유: policy 계획은 이 env가 코드에 없다고 확인함(현재 롤백=코드 되돌리기). replace S1은 "처리 코드"를 조사한다고 적어 이미 있는 것처럼 읽히고, S6 "환경변수만으로 롤백"과 S4 (a)(c) 팔(현행 프롬프트)이 성립하려면 `routerModel()`, `classifyPromptSonnet`/`classifyPromptHaiku` 상수 2개, 메트릭 router_model/router_prompt, 테스트(conductor_test.go:112 교체)가 먼저 필요함. 기본값은 sonnet 유지.
2. (S5) 게이트를 policy와 같은 정의로 고친다. 현재 불일치:
   - "티어별 오류 각 2건 이하"는 절대값, policy는 "Sonnet 해당 티어 오류 + 2건". 절대값이면 Sonnet 자체가 3건 틀릴 때 무의미하게 실패.
   - "opus->sonnet 2건 이하"도 policy는 "Sonnet 기준선 + 2건".
   - "정확도 2%p 이내"와 "총 오류 +3건"은 150개에서 같은 조건이라 중복. 하나로 합친다(+3건).
   - 오류 집계 단위(3회 평균 vs 최악)를 명시: policy는 3회 평균 오류 수, 누수만 "한 번이라도 새면 1건".
3. (S5) 일관성 단위를 명시한다: "150프롬프트 중 3회 모두 같은 티어인 비율 >= 90%". 현재는 "3회 일관성 90%"만 있어 호출 단위(450콜)로도 읽힘.
4. (S5) 빠진 policy 게이트 추가: tier 누락 0건, 파싱 실패 0건(재시도 후), 파싱된 haiku 실행 task 접미('reply: Korean 존댓말...')가 바이트 단위 100% 일치. Sonnet 기준선 누수도 참고 보고(Sonnet도 새면 라벨/규칙 문제로 판정 보류).
5. (S4) 팔 (c)의 반복 횟수를 policy와 맞춘다. replace는 (b)만 3회, (c)는 x1로 읽힘. policy는 (c) x3(비교 가능성: 일관성/누수 비교는 같은 반복수여야 함). 콜 수 1,050.
6. (S4/S5) 팔 3개의 충분성: 모델 효과와 프롬프트 효과를 분리하는 데 충분하다. 단 판정 규칙이 빠져 있음 -> "(b)가 1-3에서 (c)보다 낫지 않고 (c)가 통과하면 Haiku+현행 프롬프트로 출시"(policy)를 추가하고, 그 경우 S6 전환 대상이 (b)가 아니라 (c)임을 적는다. 추가 팔(Sonnet+새 프롬프트)은 불필요(비용만 증가).
7. (S4) 비용 점검. 추정 $1.0(Sonnet 150콜 x $0.0045 = $0.68, Haiku 900콜 x $0.0003 = $0.27, 합 약 $0.95~1.0)은 $3 상한 안이고 여유 약 3배. 보완: (i) S2 튜닝 비용(30개 x 3회 x 초안 횟수)이 상한에 포함되는지 정하고 별도 집계, (ii) 실행 순서를 (a) -> (b) -> (c)로 고정하고 팔 단위로 누적 비용 기록, (iii) 상한 도달 시 중단하면 게이트 판정이 불가하므로 "중단=실패(sonnet 유지)"로 명시, (iv) 비용은 러너 total_cost_usd 합산으로 측정(콜당 15배 가정 재확인). 비용 게이트는 구독 인증이라 실제 청구가 아닌 보고 단가임을 한 줄 주석.
8. (S2~S3 순서) 동결 -> 평가셋 순서는 맞음. 추가 조건: 동결 sha256을 평가셋 머리말에 기록, 라벨은 어떤 모델 호출 전에 저장하고 이후 변경 금지, 작성 에이전트는 프롬프트 문안을 보지 않고 티어 정의만 보게 함, 경계 사례 라벨 sonnet + 사전 표시 + 세트의 10% 이하, 예시는 개발셋/평가셋에 없는 문장. replace S3엔 이들이 없다.
9. (S2) 러너 드리프트 방지: 러너(/tmp/router3t/run.py)에 프롬프트를 수동 복사하지 말고, 빌드된 코드의 프롬프트를 덤프하는 테스트 헬퍼로 파일에 쓰고 동결 해시와 대조한다. (a)(c)의 현행 프롬프트도 같은 방식으로 해시 기록.
10. (S2) 개발셋 과적합 방지: 알려진 오류 P2/L3/P8을 "우선 확인"하는 것은 좋지만, 해당 샘플에 맞춘 예시/키워드를 프롬프트에 넣지 않는다(예시 티어당 1개, 개발셋 문장 금지). 튜닝 횟수 상한(예: 초안 5회)과 "게이트 실패 시 재튜닝 금지, 재튜닝은 새 평가셋 필요" 규칙을 S5/S6에 추가.
11. (S7 vs S6 롤백 충돌 점검) deprecated 표기 자체는 롤백과 충돌하지 않으나 조건이 필요: `classifyPromptSonnet` 문안을 현행 바이트 그대로 유지(해시 테스트), 표기는 주석/문서 문자열만, 모델 허용값 sonnet 삭제 금지. 위험: 기본값 전환 후 오타/무효 env는 기본값(haiku)로 돌아가므로 롤백 중 오타가 조용히 haiku로 남음 -> policy처럼 stderr 경고 1회를 S0에 포함. S7은 S6 이후이고 S6의 롤백 검증 이후에 하도록 순서 고정.
12. (S8) 누락된 인수 검사 추가:
   - env 테스트: unset -> 기본값; "sonnet"/"SONNET " -> sonnet; "haiku" -> haiku; "opus"/"x" -> 기본값+경고.
   - 롤백 검증: 기본값을 haiku로 바꾼 뒤 `CHAUDE_ROUTER_MODEL=sonnet`에서 선택된 프롬프트 해시 == 변경 전 sonnet 프롬프트 해시, `--model sonnet`.
   - 파서 단위 테스트 통과(파서 불변 가정), 메트릭 stage=classify에 router_model/router_prompt 기록 확인.
   - 판정 결과 표(게이트별 수치, 통과/실패)를 notes/runs/에 저장, 실패 시 LESSONS.md 기록.
   - `go build/vet/test` 외에 CHAUDE_LIVE 미설정 시 라이브 테스트가 스킵되는지 확인.
13. (제약/S6) 정책 문서 미수정 제약과 S6 기본값 전환의 충돌 가능성: DECISIONS.md의 [conductor] 줄(policy 계획 기준 32행)이 sonnet classifier를 명시하므로, 문서 승인 없이 기본값을 바꾸면 코드와 결정 기록이 어긋남. 최소한 S6을 "승인 발언 확보 후"로 묶거나, 게이트 통과 후 전환 보류 + 승인 요청으로 처리. 현재 replace는 "승인 문구 없음"을 알면서 S6은 자동 전환으로 적혀 있음.
14. (실행 담당) S1은 haiku-scout 적절. S2는 "sonnet-analyst 설계 + haiku-coder 반영"이 불필요하게 두 단계 -> 프롬프트 튜닝은 haiku-coder 1개 인스턴스가 policy대로 수행, 판정(S5)만 sonnet-analyst. S3는 haiku-drafter 새 인스턴스(policy와 일치)로 명시.
15. (열린 질문) 두 번째 질문(약 $1 vs $3)은 위 7로 해결 가능하니 질문에서 빼고 계획에 수치 근거로 넣는다.
