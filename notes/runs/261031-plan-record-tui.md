# 계획: TUI 출력 기록(record/) 및 /resume 재표시

## 목표

1. Claude TUI 출력창의 답변 내용을 프로젝트 루트의 `record/` 폴더에 저장한다.
2. `/resume`으로 저장본을 출력창에 다시 표시한다.
3. `notes/` 사용을 중단한다. 기존 `notes/runs/261031-plan-record-output.md`는 참고만 하고 수정하지 않는다.

## 결정 사항

### 결정 1. 저장 위치와 파일명

- 저장 위치: 프로젝트 루트의 `record/` 폴더.
- 파일명 형식: `record/YYYY-MM-DD-<topic-slug>[-partN].md`.
- 예: `record/2026-10-31-harness-refactor.md`, `record/2026-10-31-harness-refactor-part2.md`.

### 결정 2. 순번과 머리 줄

- 각 답변에 순번(1, 2, 3, …)을 부여한다.
- 파일 안의 각 항목 머리에 `#순번 · 시각` 형식의 줄을 둔다.
- 순번은 프로그램 재시작 후에도 이어진다. 마지막 순번은 기존 record 파일을 읽어 복원한다.

### 결정 3. 파일 분리 조건

파일을 새로 나누는 경우는 다음 세 가지다.

1. 날짜가 바뀐 경우.
2. 주제가 바뀐 경우. 훅이 내보내는 `[cat-switch: X]` 신호를 주제 변경으로 본다.
3. 용량 상한을 넘은 경우. 이때 part 번호를 올린다.

분리된 파일도 모두 인덱싱할 수 있어야 한다. 따라서 파일명과 머리 줄에 날짜와 주제를 함께 넣는다.

### 결정 4. /resume 동작

- 인자가 없으면 record 목록을 보여주고 사용자가 주제를 고른다.
- 선택한 주제의 모든 part를 순서대로 읽어 출력창에 한꺼번에 표시한다.
- 저장본을 불러오는 동안에는 record에 다시 기록하지 않는다. 재기록하면 순번과 part가 중복된다.

### 결정 5. 분석·측정 작업

- 분석 또는 측정 작업은 파일을 만들지 않는다.
- 결과는 대화창 출력으로만 응답한다.

### 결정 6. 구현 대상 파일 후보

- `internal/harness/record.go` (신규 또는 기존 초안)
- `internal/harness/record_test.go` (이미 존재)
- `tui.go`
- `resume.go`
- `repl.go`
- `CLAUDE.md` 문구

## 실행 계획

### S1. 분리 규칙 정리

1. `record.go`에 날짜, 주제, 용량 세 가지 분리 조건을 함수로 분리한다.
2. part 번호 계산 함수를 둔다. 기존 파일이 있으면 다음 part를 고른다.
3. 순번 복원 함수를 둔다. record 폴더의 마지막 항목을 읽어 다음 번호를 정한다.
4. 완료 기준: `record_test.go`에 세 분리 조건과 순번 복원 테스트가 있다.

### S2. TUI 완료 시 기록 연결

1. 답변 완료 이벤트에서 기록 함수를 호출한다.
2. 호출 전에 `[cat-switch: X]` 신호를 확인해 주제 변경 여부를 정한다.
3. 기록 실패는 출력창을 막지 않도록 오류만 표시하고 넘어간다.

### S3. 로드 함수

1. record 파일을 읽어 항목 목록을 만든다. 각 항목은 순번, 시각, 본문을 가진다.
2. 주제별로 part를 묶고 part 번호 순으로 정렬한다.
3. 로드 중 플래그를 세워 기록 함수가 동작하지 않게 한다.

### S4. /resume 선택과 일괄 표시

1. 인자가 없으면 주제 목록을 번호와 함께 보여준다.
2. 사용자가 번호를 고르면 해당 주제의 모든 part를 순서대로 출력창에 쓴다.
3. 인자로 주제 slug를 주면 목록 없이 바로 표시한다.
4. 표시가 끝나면 로드 플래그를 내린다.

### S5. repl.go 동일 동작

1. repl.go에서도 S2 기록 연결과 S4 /resume 동작을 같은 함수로 호출한다.
2. TUI와 REPL 사이에 동작 차이가 없는지 확인한다.

### S6. CLAUDE.md 문구

1. `CLAUDE.md`에 record 폴더 규칙을 적는다. 저장 위치, 파일명, 분리 조건을 포함한다.
2. `notes/` 사용 중단 문구를 함께 적는다.

### S7. 빌드와 테스트

1. `go build ./...`, `go vet ./...`, `go test ./...` 순서로 확인한다.
2. 실행은 검증 단계에서만 한다. 구현 단계에서는 실행하지 않는다.

## 수락 기준

1. 이 계획 파일이 `notes/runs/261031-plan-record-tui.md`에 존재한다.
2. 파일의 줄 수를 출력해 150줄 이하인지 확인한다.
3. 주요 헤딩(목표, 결정 사항, 실행 계획, 수락 기준)이 모두 있는지 확인한다.
4. 다른 파일은 수정하지 않는다.

## 열린 질문

1. 용량 상한의 구체적인 값(바이트 또는 항목 수)은 정하지 않았다. 구현 전에 정한다.
2. 주제 slug 생성 규칙(한글 처리 방식)은 정하지 않았다.
3. `record/` 폴더를 git에 포함할지 여부는 정하지 않았다.
