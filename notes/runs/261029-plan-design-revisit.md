# chaude 설계 재검토: 긴 컨텍스트 비용 관점 (분석 전용, 소스 수정 없음)

사용자 근거(인용): "긴 컨텍스트 사용량 때문에 설계를 그렇게 했다."
읽은 것: CLAUDE.md, DECISIONS.md(grep으로 설계 행), 261029-plan-routing-review.md, 261029-diag-background-panel.md. 비용 수치는 이 저장소 metrics로 검증하지 않았습니다(일반 원리 + 문서 근거).

## 1. 결론
서브에이전트 기반 설계는 긴 컨텍스트 근거로 여전히 성립합니다. 패널 버그는 서브에이전트 상태 추적의 결함이지 설계를 바꿀 이유가 아닙니다.

## 2. 비용 메커니즘 (일반 원리, 추정)
- 메인 세션은 매 턴 전체 히스토리를 입력으로 다시 보냅니다. 캐시가 살아 있으면 읽기 단가지만 히스토리 길이에 비례해 턴당 비용이 늘고, 캐시 TTL이 지나면 전체가 쓰기 단가로 다시 청구됩니다.
- 도구 출력(파일 읽기, 검색 결과, 빌드 로그)이 메인에 들어오면 이후 모든 턴에서 계속 재청구됩니다. 서브에이전트는 그 출력을 자기 컨텍스트에만 두고 요약만 돌려주므로 메인 히스토리가 커지지 않습니다.
- 메인을 Haiku로 고정하면 늘어난 히스토리를 읽는 단가 자체가 가장 낮습니다. Opus/Sonnet이 메인이면 같은 길이에서 턴당 단가가 더 높습니다.
- 서브에이전트 쪽 비용: 호출마다 시스템 프롬프트와 CLAUDE.md를 새로 읽고(캐시 쓰기), 같은 파일을 반복 호출하면 다시 탐색합니다. 브리프가 히스토리만큼 길어지면 이점이 사라집니다.
- 순효과(의견): 독립 작업, 큰 출력 탐색, 병렬 작업, 간헐적 사용(캐시 끊김)에서는 서브에이전트가 이깁니다. 같은 파일·결정 맥락을 5~10턴 이상 이어가는 대화에서는 메인 세션이 이길 수 있습니다(routing-review Q2와 동일).

## 3. 유지 / 변경 / 폐기

유지
- Haiku 고정 메인 + 도구 없는 메인(hook 강제) + 작업은 서브에이전트: 긴 컨텍스트의 턴당 단가와 도구 출력 누적을 동시에 막는 핵심 구조.
- 결과는 notes/runs에 쓰고 경로만 반환하는 규칙: 서브에이전트 요약이 메인에 쌓이는 양을 제한.
- 대형 작업의 계획 -> 검토 -> 병합 -> 실행 흐름(Opus/Sonnet은 개선안만 작성): 비싼 모델이 짧은 1회 컨텍스트에서만 돌아 비용 대비 효과가 좋음.
- 회전/자동 compact 장치(270k 회전, 150k compact): 메인 히스토리 비용을 직접 제어. 서브에이전트 설계와 보완 관계.

변경
- 문서 정리(최우선, 비용 무관): CLAUDE.md의 Opus 메인 전제 문단(헤더, :9, :12~:14)이 현재 Haiku 고정 구조와 충돌해 읽는 쪽(Haiku)이 혼동. "강제 Opus 메인일 때만" 구간으로 분리하거나 축소. DECISIONS.md의 target=haiku|sonnet|opus 구 설계 행에 "대체됨(:38)" 표시.
- 분류기 프롬프트 축소: model 출력이 항상 haiku로 덮이므로 size/worker 중심으로 줄이면 매 프롬프트 Sonnet 호출 비용이 줄어듦(routing-review 근거). 소규모 프롬프트는 분류 비용이 처리비보다 클 수 있음 - metrics stage=classify 집계로 확인 필요.
- 연속 작업줄기용 "세션 워커" 실험(DECISIONS.md:25~27)은 측정 결과가 나올 때까지 보류하되, 측정 기준을 정의: 같은 작업줄기 5턴 이상에서 서브에이전트 반복 비용 vs 세션 비용.
- 서브에이전트 상태 모델(아래 4): 비동기 기본값 반영.

폐기(후보, 근거는 약함)
- Haiku가 난이도를 재판단해 에스컬레이션한다는 암묵적 기대: 구현은 Sonnet 분류기 1회 태깅뿐. 문서에서 "Haiku가 판단" 표현이 있으면 제거.
- 구 Opus 메인 규칙 중 현재 경로에 쓰이지 않는 부분은 강제 Opus 시에만 필요한지 사용 빈도를 보고 삭제 검토(확신 낮음).

## 4. 배경 패널 버그가 설계에 주는 의미
- 원인(진단 문서 근거): Agent 호출에 run_in_background가 더 이상 실리지 않고 기본이 비동기인데, drain.go가 플래그가 없으면 첫 tool_result("Async agent launched...")에서 Done=true로 처리 -> 실행 중 목록이 비어 패널에 아무것도 안 뜸. 렌더링은 정상.
- 의미: 서브에이전트 중심 설계에서는 에이전트 상태 추적이 사용자에게 보이는 유일한 진행 신호이므로 이 부분의 정확성이 설계의 필수 부품. 그러나 결함은 Claude Code의 Agent 도구 기본값 변경(비동기)을 추적기가 따라가지 못한 것이며, 메인 모델/서브에이전트 구조/비용 근거와 무관. 설계 변경 사유 아님.
- 설계 교훈: (1) 상태 판정을 입력 플래그가 아니라 tool_result 텍스트/task-notification 같은 실제 수명 신호로 하고 플래그는 보조로. (2) 테스트가 명시적 run_in_background:true만 써서 실제 형태를 못 잡았음 - 실제 transcript 형태 fixture 추가. (3) 서브에이전트 의존도가 높을수록 완료 알림 누락 시 "영원히 실행 중"이 될 수 있으므로 finishOldestBackground 폴백을 플래그 무관하게 확장.
- 미검증: 라이브 TUI 실행으로 확인하지 않음(진단 문서도 동일). 동기 Agent 호출이 같은 세션에 존재하는지 불확실하여 텍스트 접두 검사가 필요.

## 5. 불확실성
- 비용 비교는 추정입니다. metrics의 classify 비용, 에이전트별 토큰, 메인 히스토리 길이 대 서브에이전트 반복 읽기 비용을 집계해야 확정됩니다.
- Haiku 고정 메인의 품질 한계(분류 오태깅 시 Haiku가 어려운 작업을 직접 수행)는 비용 근거와 별개 위험입니다.

## 6. 추천 순서
1. 패널 버그 수정(서브에이전트 상태): tool_result 접두 검사 + 실제 형태 테스트.
2. CLAUDE.md/DECISIONS.md의 Opus 메인 구 규칙 정리.
3. metrics에서 classify 비용 대비 처리비 집계 후 분류기 프롬프트 축소 여부 결정.
