# Opus 상시 메인(캐시 재사용) 비용 분석

date: 261029
근거 범위: 3-세션 계획(261029-plan-three-session-structure.md)과 약점 분석(261029-analysis-three-session-weakness.md)에 적힌 사실만 사용했습니다. 가격은 저장소에서 확인된 것이 없어 쓰지 않았고, 단가는 상대 비교(캐시 읽기 << 입력 << 캐시 쓰기)로만 다룹니다. 저장소에서 확인되지 않은 수치는 모두 "가정"으로 표시했습니다.

저장소에서 확인된 사실
- 캐시 TTL 1시간으로 고정, 유휴 핸드오프 59:59 (DECISIONS:23, 계획 인용)
- 컨텍스트 한도 opus/sonnet 270k, haiku 80k (repl.go:26-27, :870)
- haiku-scout 출력은 5줄 이하이고 원문 붙여넣기를 금지합니다 (계획 "데이터 흐름")
- 설계 세션 회전 시 핸드오프는 설계 파일 경로 목록과 미결 항목뿐입니다 (계획 "컨텍스트 한도")
- 유휴 회전/자동 종료는 코드에 아직 없습니다 (약점 분석 W8)

## 비교

대상: (A) Opus 메인 상시 유지, (B) 설계 작업마다 새 Opus 세션을 열고 설계 파일로 복원, (C) Haiku 메인에 Opus는 설계 검토 때만 호출.

### 비용 구조 (상대 비교)
| 항목 | A | B | C |
|---|---|---|---|
| 턴당 비용 | 컨텍스트 C 전체의 캐시 읽기. C가 커질수록 선형 증가 | 새 세션이라 C가 작고, 턴당 읽기도 작음 | Opus 턴이 드묾. Haiku 턴은 값싼 단가 |
| 시작 비용 | 최초 1회 캐시 쓰기 | 작업마다 설계 파일 + 시스템 프롬프트를 캐시 쓰기로 다시 지불 | 검토 호출마다 검토 대상 입력을 새로 지불 |
| 유휴 1시간 초과 | 다음 턴에 C 전체를 캐시 쓰기로 재지불. 핑(59:59)으로 막으면 무작업 시간에도 비용 발생 | 영향 없음. 세션이 이미 없으니 쓰기 비용은 B의 시작 비용과 같음 | Opus가 안 떠 있으니 영향 없음 |
| 무작업 시간 | 핑을 쓰면 시간당 고정비 | 0 | 0 |

핵심 산식 (가정: 단가 관계만 쓴 비교식)
- A의 누적 비용 ≈ 첫 쓰기(C0) + 턴마다 읽기(C0 + 증가분). 턴 n에서 읽기 비용은 n에 비례해 커지고, 총합은 n에 대해 대략 제곱으로 늘어납니다.
- B의 작업당 비용 ≈ 설계 파일 쓰기(F) + 그 작업 안의 턴(작은 C). F는 설계 파일 + 시스템 프롬프트 크기입니다.
- 교차점: A가 유리한 조건은 "복원 대상 F를 다시 쓰는 비용 > 같은 구간 동안 A가 추가로 내는 읽기 비용"입니다. 쓰기는 읽기보다 비싸므로(가정: 상대 관계만, 배율 미확인), 캐시가 살아 있고 C가 아직 작을 때는 A가 이깁니다. C가 커지거나 캐시가 죽으면 B가 이깁니다.

### 캐시 만료
- A는 1시간 안에 다음 턴이 오면 읽기만 내고, 넘으면 C 전체를 다시 씁니다. C가 클수록 그 한 번의 손실이 큽니다.
- 계획 Q7(핑 vs 만료 후 재읽기)이 미결입니다. 핑은 "대화 간격이 1시간보다 조금 긴" 패턴에서만 이득이고, 한참 쉬는 패턴에서는 낭비입니다. 사용자 패턴 통계가 저장소에 없으므로 어느 쪽이 이득인지 현재 판단할 수 없습니다.
- B는 만료가 문제가 아니라 설계의 전제입니다. 단, 설계 작업 사이 간격이 짧으면(1시간 이내) A가 가진 살아 있는 캐시를 B가 버리는 셈입니다.

### scout 결과 누적과 270k
- 계획상 scout 출력은 5줄 이하라서 한 번에 들어오는 양은 작습니다. 5줄을 약 500자로 보면 몇 백 토큰 수준입니다(가정).
- 하지만 Opus 컨텍스트에는 scout 결과 외에도 설계 파일 작성 내용, 사용자 대화, 도구 호출 입력, Opus 자신의 출력이 쌓입니다. 270k를 채우는 주된 요인은 scout 결과가 아니라 이것들일 가능성이 큽니다(추정, 측정 없음).
- 위험은 규약 위반입니다. scout가 5줄 제한을 어기거나 Opus가 Read로 직접 큰 파일을 열면 한 번에 수 만 토큰이 들어옵니다. 약점 분석 W3와 같은 맥락입니다.
- 270k 도달 시 A는 회전하고, 핸드오프는 경로 목록과 미결 항목뿐입니다. 즉 A도 회전 시점에는 B와 같은 "설계 파일 복원"을 합니다. A와 B의 차이는 복원을 매 작업마다 하느냐, 270k마다 하느냐입니다.
- 회전 빈도는 측정된 적이 없습니다. 이 분석의 가장 큰 불확실성입니다.

### B의 손실 핸드오프 품질 위험
- 설계 파일에는 evidence(path:line)와 brief가 있습니다. 결정의 이유, 기각한 대안, 사용자 정정의 뉘앙스는 파일에 기록되지 않으면 사라집니다.
- 계획은 파일 갱신 규칙이 없습니다(약점 분석 W10 드리프트). B는 파일이 곧 유일한 기억이라 이 약점이 직접 품질 문제가 됩니다.
- 완화: 파일에 `## decisions`(결정과 기각 사유), `## open` 절을 필수로 두고, 사용자 정정은 즉시 파일에 반영하는 규칙을 둡니다. 이 완화를 쓰면 B의 품질 위험은 줄어들지만, Opus가 매번 기록해야 하므로 출력 토큰이 늘어납니다.
- A는 대화의 뉘앙스를 컨텍스트로 보존하지만, 270k 회전 때 B와 같은 손실을 한 번은 겪습니다.

### 지연
- A: 캐시 적중 시 첫 토큰이 가장 빠릅니다. 만료 후 첫 턴은 느립니다(전체 재처리).
- B: 매 설계 작업의 시작에 파일 읽기 + 세션 기동이 직렬로 붙습니다. 계획 W4(직렬 지연)에 더해 세션 기동이 추가됩니다.
- C: 일반 턴은 Haiku라 가장 빠르지만, 설계 검토 호출은 Opus 입력을 새로 보내야 하고 검토 결과가 Haiku 메인을 거쳐 사용자에게 가므로 설계 품질 경로가 한 단계 더 깁니다.

### C의 별도 위험
- 사용자 정정 1번("Opus 설계 세션은 항상 존재")과 DECISIONS:38(main Haiku 고정)의 충돌을 계획이 사용자 쪽으로 해소한 상태입니다. C는 그 정정을 되돌리는 안이라 사용자 확인 없이는 선택할 수 없습니다.
- Haiku 메인은 컨텍스트 한도가 80k이고 설계 판단 품질이 낮습니다. 오분류 시 설계 이득이 사라집니다(W6, W9).

## 조건별 판단

### 1. 잦은 왕복 (설계 대화가 1시간 안에 계속 이어짐)
- 추천: A.
- 이유: 캐시가 계속 살아 있고, 컨텍스트가 작은 초반에는 읽기 비용이 낮습니다. B는 작업마다 쓰기 비용을 반복해서 내고, 대화 뉘앙스 손실도 매번 겪습니다.
- 조건: C가 커져서 회전 임계(270k)에 가까워지면, 회전 직전에 설계 파일에 결정을 기록해 둡니다. 회전은 A의 정상 동작이므로 별도 전환은 필요 없습니다.
- 주의: 회전 빈도가 높으면(예: 몇 시간에 여러 번) B에 가까운 비용이 되므로, A의 이득은 "회전 간격 내 턴 수"에 달려 있습니다.

### 2. 가끔 설계 (설계 요청 사이 간격이 1시간 이상)
- 추천: B(또는 계획 약점 분석 W1의 "지연 생성": 필요할 때만 세션을 만들고, 1시간 유휴 후 핑 없이 종료).
- 이유: A는 캐시가 이미 죽은 뒤 첫 턴에서 전체 재처리 비용을 내며, 핑을 쓰면 무작업 시간에도 비용이 듭니다. 어느 쪽이든 A의 "항상 존재"는 이득이 없습니다.
- 조건: 설계 파일에 decisions/open 절을 필수로 둡니다. 안 두면 B의 손실 핸드오프 위험이 그대로 남습니다.

### 3. 혼합 (오전에 몰아서 설계, 이후 며칠 조용)
- 추천: A를 기본으로 하고, 유휴 1시간 후 핑 없이 종료한 뒤 다음 설계 턴에서 B 방식으로 재개(= W1 지연 생성). 사실상 A와 B의 하이브리드입니다.
- 이유: 작업 중에는 A의 이득을 얻고, 쉬는 동안에는 B의 비용 0을 얻습니다. 계획이 "항상 존재"를 "논리적으로 항상 존재"로 해석하면 사용자 정정과도 양립합니다(약점 분석 Q1이 같은 질문).

### 4. C를 고려할 때
- 설계 요청이 매우 드물고(하루 몇 번 미만, 가정) 대부분이 작은 조회/수정인 경우에만 C가 이깁니다. 이 경우에도 사용자 정정 1번과 충돌하므로 사용자 확인 없이는 권하지 않습니다.

### 종합 판단
- 한 줄: 단순 A 상시 유지도, 단순 B도 아니고, "A로 시작해 1시간 유휴 시 종료하고 설계 파일로 재개하는 하이브리드(W1 지연 생성)"가 두 패턴 모두에서 손실이 가장 작습니다. 이는 추정이며 실측이 필요합니다.
- 측정 없이 A 또는 B를 고정하는 것은 권하지 않습니다. 먼저 metrics에 Opus 턴 사유, 세션 컨텍스트 크기, 턴 간격을 기록하고(W2 보완과 동일) 몇 일치를 본 뒤 결정하는 편이 안전합니다.

## 뒤집히는 가정

| 가정 | 현재 가정 | 뒤집히면 |
|---|---|---|
| 사용자의 설계 요청 간격 | 짧은 구간(1시간 이내)과 긴 휴지가 섞임 | 대부분 1시간 이내면 A 확정. 대부분 1시간 초과면 B 확정 |
| 캐시 쓰기와 읽기의 비용 배율 | 쓰기가 읽기보다 훨씬 비쌈(상대 관계만 확인, 배율은 가정) | 배율이 작으면 만료 손실이 작아 B/하이브리드의 이점이 줄고 A가 더 낫습니다. 배율이 크면 반대 |
| 270k 회전 빈도 | 낮음(scout 5줄 규약 유지 시) | 규약이 지켜지지 않아 자주 회전하면 A의 읽기 비용이 커지고 B에 가까워집니다 |
| 설계 파일에 결정/기각 사유가 충분히 기록됨 | 규약으로 보장 가능 | 기록이 부실하면 B의 품질 손실이 커져 A 쪽으로 기웁니다 |
| 사용자 정정 1번의 "항상 존재" 해석 | 논리적 존재도 허용 | 반드시 live 프로세스여야 하면 B와 하이브리드가 불가능하고 A만 남습니다 |
| Opus 설계 호출 빈도 | 중간 | 매우 드물면 C가 유리해집니다(단, 정정 1번 충돌) |
| 핑 비용 | 무작업 시간에도 비용이 발생 | 핑 호출이 사실상 무료에 가깝다면(정책/요금 확인 필요) A 상시 유지가 하이브리드보다 낫습니다 |

가장 민감한 변수 두 개: (1) 설계 요청 간격 분포, (2) 캐시 쓰기/읽기 배율. 둘 다 저장소에 없는 값입니다.

## 열린 질문

1. 사용자의 실제 설계 요청 간격 분포는 어떻습니까? metrics 2026-10-28/29에서 Opus 턴 간격을 뽑아볼 수 있는지 확인이 필요합니다(이 분석에서는 열어보지 않았습니다).
2. 현재 사용 모델의 캐시 쓰기/읽기 단가 배율은 얼마입니까? 공식 가격표를 확인한 뒤 위 표의 "가정"을 확정해야 합니다(이 분석은 가격을 만들어 쓰지 않았습니다).
3. 정정 1번 "항상 존재"는 live 프로세스인가, 필요 시 재개 가능한 논리적 존재인가? (계획 Q7, 약점 분석 Q1과 동일. 이 답이 하이브리드 가능 여부를 정합니다.)
4. scout 5줄 제한은 코드로 강제됩니까, 프롬프트 규약뿐입니까? 규약뿐이면 270k 도달 속도의 상한을 보장할 수 없습니다.
5. 설계 파일에 `## decisions`와 `## open` 절을 필수로 추가하는 것을 계획에 반영해도 됩니까? (이 분석은 계획을 수정하지 않았습니다.)
6. 핑(59:59) 호출이 비용 없이 캐시만 갱신하는지, 실제 입력 토큰 과금이 되는지 확인이 필요합니다.
