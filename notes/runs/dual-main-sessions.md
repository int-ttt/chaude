# 메인 세션 이중 운영(Sonnet/Opus 병행) 적합성 판단

작성: 2026-10-29. 코드 수정 없음. 근거: notes/runs/model-split-vs-switch.md, usage-analysis.md, routing-redesign.md, internal/harness/classifier.go(pickModel/route), repl.go(rotate 536행~). 단가는 이 세션에서 재확인하지 않은 가정입니다(Opus 캐시 쓰기 $6.25/M, 읽기 $0.50/M, Sonnet 쓰기 $3.75/M, 읽기 $0.30/M).

## 0. 판단
- 이중 메인 세션은 기본 방식으로는 부적합합니다. 현행(Opus 메인 유지 + 서브 위임)을 유지하고, 이중 운영은 "두 모델이 5분 안에 자주 번갈아 쓰이는" 좁은 조건에서만 이득이 있습니다(추정).
- 현행 대비 이득이 있을 수 있는 것은 "rotate 전환"과의 비교입니다. 하지만 rotate 전환이 문제였던 이유(분류기가 Opus/Sonnet을 오가게 해서 8회 왕복)는 이미 pickModel 재설계로 제거되었습니다. 이중 운영은 이미 줄어든 문제를 푸는 셈입니다.

## 1. 근거(증거)
- 전환(rotate) 1회 실측: 11.7~23초 지연(Opus행 평균 약 15초, Sonnet행 약 22초), 새 세션 cache_creation 약 26k(22k~40k), 인계 노트 턴 1회. 10-29에 8회 발생(전부 reason이 route). 출처 model-split-vs-switch.md 1-2절.
- 현재 코드: pickModel은 cur가 opus 또는 빈 값이면 항상 opus를 반환하고, topic=new+size=small일 때만 delegate=true로 서브 위임합니다. Sonnet 메인은 사용자가 강제한 경우뿐이고 new+large면 opus로 갑니다(classifier.go 31~39행). 즉 재설계 후 정상 경로에서는 모델 전환 자체가 드뭅니다. 재설계 이후 실제 전환 감소는 live 미검증(routing-redesign.md).
- 구조: Repl은 자식 세션 하나(`r.sess`)와 그에 묶인 상태(tracker, lastCtx, pendingSnapshot, files, draining)를 전제로 합니다. route()는 모델이 다르면 `r.a.Model`을 바꾸고 rotate를 부릅니다(classifier.go 116~125행). 이중 운영은 이 전제를 깨야 합니다.

## 2. 비용 비교(자릿수 수준, 가정 단가)
| 항목 | 현행(Opus 유지+위임) | rotate 전환 | 이중 세션 |
|---|---|---|---|
| 전환 시 지연 | 없음 | 약 15~22초 | 따뜻한 세션이면 없음, 식은 세션이면 재캐시(첫 응답 지연 증가, 미측정) |
| 전환 시 토큰 | 서브 브리프+서브 캐시 쓰기 약 3k | 새 세션 쓰기 약 26k+인계 턴(약 $0.15~0.25) | 따뜻함: 상대 세션이 못 본 턴 요약 주입분만. 식음: 전체 컨텍스트 재캐시 |
| 캐시 | 메인 캐시 유지 | 전환마다 폐기 | 세션별 유지, 단 TTL 만료 시 소실 |
| 맥락 | 단일 | 인계 노트로 압축(손실 위험) | 분기(두 세션이 서로 다른 것을 앎) |
| 프로세스 | 자식 1(+드레인) | 자식 1(+드레인) | 상시 자식 2 |

식은 세션 재캐시 추정(가정 단가): 컨텍스트 40k면 Opus $0.25, Sonnet $0.15. 100k면 Opus $0.63, 270k면 Opus $1.7. 읽기(캐시 적중)는 40k Opus 약 $0.02. 즉 적중 시 쓰기의 약 1/12.
- TTL이 5분이라는 가정이 핵심 불확실점입니다. 한국어 코딩 대화에서 사용자 입력 간격이 5분을 넘기는 일은 흔해서, 두 세션 중 쉬고 있던 쪽은 대체로 식어 있을 것으로 추정됩니다(실제 간격 분포는 미측정). 식어 있으면 이중 운영의 "각자 캐시 유지" 이점이 사라지고, 쉬는 세션의 맥락이 그만큼 낡습니다.
- 반대로 한 세션만 계속 쓰면 다른 세션은 거의 유휴이므로 이중 운영은 프로세스·낡은 맥락 비용만 남깁니다.

## 3. 쟁점별 판단
1. 전환·압축 비용 vs 분리 비용: 이중 세션이 아끼는 것은 rotate의 약 26k 쓰기+인계 턴+15~22초입니다. 하지만 라우팅이 Opus 고정에 가까워진 지금 전환 빈도 자체가 낮아 절감 총량이 작습니다(추정).
2. 맥락 동기화: 가장 큰 숨은 비용입니다. 한 세션이 한 일을 다른 세션이 모르므로, 모델을 넘길 때마다 "그 사이 일어난 일" 요약을 주입해야 합니다. 이는 결국 rotate의 인계 노트와 같은 종류의 작업(요약 품질 위험 포함)을 더 자주, 부분적으로 하는 것입니다. 놓친 변경(파일 수정, 결정)을 못 전하면 두 세션이 충돌하는 수정을 할 수 있습니다.
3. 장기 컨텍스트 증가: 세션이 둘이면 각자 270k 임계값(repl.go 816행) 도달 시기가 다르고 rotate/압축이 세션별로 따로 필요합니다. 주입된 요약까지 쌓이므로 합산 컨텍스트는 단일 세션보다 커집니다(추정).
4. 메모리/프로세스: 자식 claude 프로세스 2개 상시 유지. 메모리 수치는 측정하지 않았습니다. 드레인(rotate 후 서브에이전트 완료 대기) 로직도 세션별로 두 벌입니다.
5. 라우터 정책과의 관계: 현재 pickModel은 "Opus 고정+위임"이라는 목적이므로 이중 운영과 정책이 충돌합니다. 이중 운영을 하려면 pickModel이 "어느 세션으로 보낼지"를 반환하는 의미로 바뀌고, "new+small은 위임"이라는 현행 경로와 "Sonnet 세션으로 보냄"이라는 경로가 겹칩니다(위임이면 서브에이전트가 이미 싼 모델을 씀). 즉 Sonnet 메인 세션의 존재 이유가 서브 위임과 상당 부분 중복됩니다.

## 4. 조건부로 적합한 상황
- 사용자가 두 종류의 장기 작업(예: Opus로 설계, Sonnet으로 반복 구현)을 번갈아 하고, 전환 간격이 대부분 5분 이내이며(캐시 유지), 각 세션의 컨텍스트가 100k를 넘어 재캐시가 비쌀 때.
- 두 작업의 맥락이 서로 독립적일 때(동기화 비용이 작음). 이 경우 사실상 "병렬 프로젝트 2개"이므로 이미 별도 chaude 인스턴스로 해결 가능합니다.
- 위 조건이 아니면 현행(위임)이 단순하고 싸다고 판단합니다.

## 5. 구현 시 필요한 변경(이중 운영을 한다면)
1. Repl의 단일 상태(`sess`, `tracker`, `lastCtx`, `pendingSnapshot`, `files`, `draining`, rotation 카운터)를 세션별 구조체 두 개로 분리.
2. route(): 모델이 다르면 rotate 대신 활성 세션 포인터 전환. 대상 세션이 없으면 새로 시작.
3. 동기화: 비활성 세션이 못 본 턴 목록을 추적(`tr.turns`에 세션 태그 필요)하고, 전환 시 델타 요약을 프롬프트 앞에 주입. 요약 방식(결정적 스냅샷 vs LLM 요약)과 검증(validateHandoff 재사용 여부) 결정 필요.
4. TTL 관리: 마지막 활동 시각 기록, 만료 임박/만료 시 정책(재캐시 감수 vs 해당 세션 폐기 후 인계로 시작).
5. 종료·메트릭·재개(resume.go): 세션 2개를 저장/복원하도록 변경, 메트릭에 session 구분.
6. pickModel 의미 변경과 TestMainRouteSwitchPolicy 등 기존 테스트 재작성. 대략 repl.go, classifier.go, core.go, resume.go, drain.go, tui.go(상태 표시)에 걸쳐 5개 이상 파일이 얽힙니다.
- 난이도: 높음(상태 분리가 핵심이며, 현행 단일 세션 가정이 코드 전반에 퍼져 있음). 비교로 rotate 전환 정책 조정(히스테리시스)은 한 함수 수준의 작은 변경입니다.

## 6. 대안(더 싼 개선)
- 현행 유지 + route 후 Opus가 위임 힌트를 따르는지 재측정(model-split-vs-switch.md 3절 3번).
- Sonnet 메인이 Opus 서브를 55회 쓴 역행 방지(규칙 또는 훅).
- 이중 운영을 검토하기 전에 사용자 입력 간격(TTL 초과 비율)과 전환 빈도를 재설계 후 메트릭에서 먼저 측정.

## 7. 불확실점
- 캐시 TTL(5분 가정)과 모델 간 캐시 비공유는 공식 재확인하지 않았습니다.
- 단가는 가정이며 usage-analysis의 cost_usd와 검산이 맞지 않았습니다(model-split-vs-switch.md 1-3절). 달러는 자릿수만 참고하세요.
- 재설계 이후 실제 전환 빈도, 사용자 입력 간격 분포, 자식 프로세스 메모리, 동기화 요약의 품질 손실은 모두 미측정입니다.
- 인계 노트 턴의 토큰/비용은 메트릭에 필드가 없습니다.
