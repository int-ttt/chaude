## 약점

### 비용
- W1 Opus 상시 유지 비용. [근거] 설계 세션은 항상 존재하고 캐시 TTL 1시간(DECISIONS:23) 가정. [추정] 1시간 넘게 쉬면 다음 턴에 전체 컨텍스트를 캐시 쓰기로 다시 지불하거나, 59:59 핑으로 유지하면 아무 일도 안 해도 시간당 비용 발생. 계획 Q7이 미결.
- W2 프롬프트당 Opus 턴. [근거] 계획은 분류 로그를 파일로 두고 설계 턴/keep-end 시점에만 Opus가 읽도록 해서 작은 haiku 경로는 Opus를 깨우지 않음. [추정] 그래도 model=opus 와 size=large 는 모두 Opus 턴이고, keep/end 판단이 "새 세션 시작 시"에도 발생하면 중간 크기 작업마다 Opus 턴이 붙음. 결국 Opus 컨텍스트가 270k에 빨리 접근.
- W3 opus 선택 시 설계 세션이 직접 처리(가정). [추정] 설계 대화와 실행 이력이 한 컨텍스트에 쌓여 270k 회전이 잦아지고, 매 회전 handoff 비용이 Opus 단가로 발생.

### 지연
- W4 라우팅 직렬 지연. [근거] 큰 작업은 설계 파일 완료(존재+size>0+2초 안정) 후 실행 세션 시작. [추정] 분류(1회) + Opus 설계 + 2초 안정 대기 + 실행 시작이 직렬이라, 사용자는 첫 토큰까지 가장 긴 경로를 기다림. 오분류 시 Opus 설계를 기다린 뒤에야 오류가 드러남.
- W5 keep/end 판단 지연/차단. [추정] Opus가 판단하는 동안 새 프롬프트가 들어오면 판단 결과를 기다리는지, 그냥 진행하는지 규칙 없음. 판단이 응답 경로에 끼면 지연, 끼지 않으면 stale 세션 위험.

### 실패 모드
- W6 분류자 오분류. [근거] model 줄 누락/무효 시 size/kind 폴백(안전쪽 large). 계획 Q2에서 Opus가 모델을 바꿀 수 있는지 미결. [추정] haiku로 잘못 가면 80k 한도에서 실패하거나 품질 저하, opus로 잘못 가면 과금. 정정 신호를 잡는 경로(2회 실패 시 상향)가 없음.
- W7 Opus 사용 불가(한도/오류/지연). [추정] 계획에 없음. 설계 세션이 죽으면 large/opus 경로 전체 정지, keep/end 응답 없음. [근거] 파싱 실패/무응답 = end 이므로 모든 kept 세션이 일괄 종료되어 캐시 이득 소멸.
- W8 stale kept 세션. [근거] 유지 창 last_used+3570초 후 자동 종료는 코드에 없음(유휴 회전 미구현). [추정] 구현 전에는 kept 세션이 무한 잔존하거나 TTL 지난 세션이 전체 캐시 쓰기를 내며 재사용됨. "비슷한 작업" 판정이 라벨/파일 겹침뿐이라 오탐 시 낡은 컨텍스트로 답할 위험.
- W9 haiku 80k 초과. [근거] 한도 도달 시 답변 후 rotate+handoff, 백그라운드 에이전트 있으면 draining. [추정] 큰 단일 답변이나 대용량 Read 한 번으로 80k를 한 턴에 넘길 수 있고(답변 후에야 검사), handoff 요약도 haiku가 쓰면 품질이 낮음. 설계 파일 brief(≤3,000자)가 있어도 도구 출력이 지배적일 수 있음.

### 상태 일관성
- W10 설계 파일 드리프트. [추정] 설계 파일은 Opus가 한 번 쓰고, 이후 실행 세션이 결과를 바꾸거나 사용자가 정정해도 파일이 갱신된다는 규칙이 없음. 오래 kept된 실행 세션은 낡은 brief를 계속 보유, 설계 세션 회전(270k) 시 handoff가 경로 목록만이므로 "파일이 최신인지"를 검증할 수단 없음.
- W11 이중 소스. 상태가 설계 파일(디스크), route-log(디스크), parked/workerPool(메모리), Opus 컨텍스트(세션)에 분산. [근거] workerPool은 메모리(최대 5 후보). [추정] 재시작 시 workerPool은 사라지고 설계 파일/route-log만 남아 keep/end 판단 입력(files, last_used)이 불일치.
- W12 세션 ID 승계. [근거] rotate 시 새 id가 keep/end 상태와 workerPool/parked 항목을 이어받아야 함(리뷰 6). 구현 없으면 회전 직후 판단 기록이 끊김.

## 보완

형식: 약점 -> 보완 / 보완 비용 / 시점.

- W1 -> Opus 설계 세션을 "지연 생성": 첫 large/opus/판단 필요 시점에 만들고, 1시간 유휴 후에는 핑 없이 종료하고 설계 파일 경로 목록으로 다음 턴에 재개. 계획의 "항상 존재"는 "논리적으로 항상 존재(필요 시 재개)"로 해석. / 비용: 재개 첫 턴 캐시 쓰기 1회 + 재개 로직(parked id resume 재사용, 중간). 사용자 정정 1번과 충돌 소지 있어 확인 필요(Q1). / 시점: 지금 결정(방침), 구현은 나중.
- W2 -> Opus 호출 예산: 유형별 상한(model=opus/large/판단 필요 시점만). keep/end는 배치 판단(여러 세션을 한 번에, 유휴 만료 직전 또는 세션 수가 상한 초과 시). metrics에 Opus 턴 사유를 기록해 계획의 확인 항목("작은 haiku는 Opus 턴 없음")을 자동 검증. / 비용: 낮음(metrics 필드 추가 + 조건문). / 시점: 지금.
- W3 -> opus 직접 처리는 유지하되, 실행형 작업(편집 다수)은 opus-architect 서브에이전트로 위임해 설계 세션 컨텍스트를 보호. 설계 세션에는 요약만 반환. / 비용: 서브에이전트 호출 오버헤드(낮음), 기존 규칙(DECISIONS:36 요약 반환) 재사용. / 시점: 나중(회전 빈도 측정 후).
- W4 -> 설계가 필요 없는 large(분석/검토 sonnet)는 설계 파일 대기 없이 즉시 시작. 대기는 model=opus 이거나 분류자가 `needs_design: yes` 일 때만. 안정 대기 2초는 유지(작음). / 비용: 분류자 출력 1줄 + 테스트 케이스(낮음). / 시점: 지금(분류자 model 줄 구현과 함께).
- W5 -> keep/end는 비동기: 응답 경로에서 기다리지 않고, 판단 전 기본값 = keep(유지 창 내). 판단 결과는 다음 입력 전에 반영되면 반영, 아니면 만료 시 적용. / 비용: 낮음(타이머 + 기본값). / 시점: keep/end 구현 시.
- W6 -> (a) 상향 규칙: 같은 작업이 haiku에서 2회 실패하면 sonnet, 이후 opus 로 자동 상향(기존 "Haiku 2회 실패 시 Sonnet" 취지와 일치, 근거는 에이전트 설명 문구). (b) 분류 결과를 route-log에 남겨 Opus가 오분류를 사후 교정(Q2의 답으로 "설계 턴에 한해 교정 허용"). (c) 오분류율을 TestClassifierLive 확장 + metrics routed_model 로 측정. / 비용: (a) 중간(실패 판정 정의 필요), (b)(c) 낮음. / 시점: (c) 지금, (a)(b) 나중.
- W7 -> 폴백 경로: Opus 호출 실패 시 (1) keep/end 응답 없음은 end가 아니라 "현 상태 유지 + 만료 시 종료"로 변경, (2) large/opus 작업은 sonnet 실행 세션으로 강등하고 사용자에게 한 줄 알림, (3) 재시도 1회. / 비용: 낮음~중간(오류 분류 + 강등 분기). / 시점: keep/end 구현과 동시에 (무응답=end 가정은 지금 바꾸는 편이 안전).
- W8 -> (a) 자동 종료 타이머를 keep/end보다 먼저 구현(3570초 하드 상한). (b) "비슷한 작업" 오탐 방지: 라벨 일치 AND 파일 겹침 중 하나가 아니라, 재사용 시 handoff 없이 이어쓰되 설계 파일 mtime이 세션 시작보다 새로우면 재사용 거부. / 비용: (a) 낮음, (b) 낮음. / 시점: (a) 지금, (b) 설계 파일 도입 시.
- W9 -> (a) 80k 사전 검사: 도구 출력 크기가 큰 작업(대용량 Read)은 분류자 size=large 이면 haiku 금지(상한: haiku는 small만). (b) 임계값을 80k의 약 75%(예: 60k)에서 "다음 큰 작업 전 회전" 소프트 한도로 둠. (c) handoff 요약은 haiku가 아닌 sonnet이 작성(드문 호출). / 비용: (a) 낮음, (b) 낮음(상수), (c) 낮음(호출 1회). / 시점: (a) 지금(라우팅 규칙에 포함), (b)(c) 나중. 수치 60k는 [추정]이며 측정 후 조정.
- W10 -> 설계 파일에 `version`(mtime 또는 증분 번호)과 `status: draft|final|superseded` 헤더를 둠. 실행 세션 brief는 version을 함께 보유, 변경 시 kept 세션을 end 대상으로 표시. 사용자 정정 시 Opus가 파일을 갱신하면 파일이 단일 진실원. / 비용: 중간(헤더 규약 + 비교 로직). / 시점: 설계 파일 구현 시.
- W11 -> 상태를 한 곳에 영속화: workerPool/parked를 상태 디렉터리 JSON(이미 subagent state 영속화가 0.7.0에 있으므로 같은 패턴 재사용)에 쓰고, route-log는 그 항목을 가리킴. 재시작 시 복원. / 비용: 중간. / 시점: 나중(keep/end 도입 후, 재시작 빈도가 문제될 때).
- W12 -> rotate()에서 새 id로 keep/end 항목과 pool 항목을 옮기는 단위 테스트 1개 추가. / 비용: 낮음. / 시점: 세션별 임계값 구현과 동시에.

## 코드와의 차이

[근거: 리뷰가 확인한 코드 사실]
- 분류자 출력은 topic/size/kind/worker/task뿐, model 줄 없음(classifier.go:15-23). pickModel/pickTarget은 항상 Haiku 고정(:39-52). -> 3-세션 라우팅 자체가 없음.
- Repl은 live 세션 1개(r.sess) + parked 맵 + draining. 동시에 둘 이상 live 세션 없음(repl.go:157). -> 설계 세션과 실행 세션이 동시에 존재하는 구조는 새 소유권 모델이 필요.
- 모델 전환은 순차(한 번에 한 main, 카테고리 전환/임계값 시 rotate). 병행 실행 세션 없음. effectiveThreshold는 현재 r.a.Model 하나만 봄(repl.go:695).
- 유휴 회전/자동 종료는 non-test 코드에 없음(DECISIONS:19/21/23은 문서만).
- 컨텍스트 한도: opus/sonnet 270k, haiku 80k는 코드와 일치(repl.go:26-27, :870). 자식 compact 창 400k > 270k도 일치.
- haikupool.go workerPool은 메모리, 최대 5 후보. keep/end의 입력(files)은 여기서 얻을 수 있으나 영속화되지 않음.
- planHint(classifier.go:32-34), TestHaikuPlanWorkflow는 "Haiku가 계획 작성" 가정 -> 3-세션 구조와 반대. 구현 시 제거/보존 결정 필요.

[추정] 차이의 크기: 가장 큰 간극은 "동시 다중 live 세션". 현재 코드는 순차 전환 모델이라, 설계 세션 상시 존재 + 실행 세션 병행은 Repl 세션 소유권을 바꾸는 큰 변경(리뷰 ordering에서 2-3단계가 설계 패스 필요라고 한 것과 일치). 중간 단계로 "순차 전환 유지 + 설계 파일만 디스크 계약으로 도입"하면 병행 없이도 W4, W10, W2 일부를 검증할 수 있음. 이것이 단계적 이행안 후보.

2. W7: Opus 사용 불가 시 large/opus 작업을 sonnet으로 강등해도 되는가, 아니면 사용자에게 중단을 알리는가?
3. W6: 오분류 정정은 자동 상향(2회 실패)으로 충분한가, Opus가 설계 턴에서 모델을 바꿀 수 있어야 하는가(계획 Q2와 동일)?

6. 이행안: 병행 live 세션 대신 순차 전환 + 설계 파일 계약을 1단계로 하는 것에 동의하는가?
