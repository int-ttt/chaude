# 다중 모델 분산(Opus 메인 + 서브에이전트) vs 메인 모델 전환 비교

작성: 2026-10-29. 코드 수정 없음. 수치는 notes/metrics/2026-10-28·29.jsonl 재집계와 internal/harness 코드 확인에 근거합니다.

## 0. 결론
- 권장: Opus 메인을 유지하고 작은 작업은 Haiku/Sonnet 서브에이전트로 보내는 방식(현재 방향)을 기본으로 합니다. 메인 모델 전환은 사용자가 명시했거나 "새 주제 + 큰 작업"일 때만 허용합니다.
- 지금 가장 큰 낭비는 모델 분산 방식이 아니라 "route 전환마다 세션 교체"가 10-29에 8번 일어난 것입니다.
- 38~44k 교체는 컨텍스트 임계값(270k) 때문이 아닙니다. 모델이 바뀌면 코드가 무조건 rotate를 부르기 때문입니다(2절).

## 1. 근거 (증거)
### 1-1. 38~44k에서 교체되는 이유 (코드·메트릭으로 확인)
- classifier.go `route()`: 분류 결과 모델이 `r.a.Model`과 다르면 `r.a.Model = model` 후, 대화 기록이 있으면 `r.rotate("route "+model)`를 호출합니다. 컨텍스트 크기를 보지 않습니다.
- 270k 임계값은 repl.go 716행 `ctx >= threshold` 경로에서만 쓰입니다. 10-29 rotate 8건의 reason은 전부 `route opus`/`route sonnet`이고 ctx 교체는 0건입니다.
- 38~44k는 교체 시점의 현재 크기일 뿐입니다. 새 세션은 첫 턴부터 이미 cache_creation 약 26k(시스템 프롬프트+CLAUDE.md+도구 정의로 추정)가 들어 있어, 1~2턴이면 38~44k가 됩니다. 즉 세션이 커지기 전에 모델이 바뀌어 교체되는 것입니다.
- 10-29 교체 8건 모두 opus와 sonnet이 번갈아 나왔습니다(분류기가 같은 날 opus 8회/sonnet 7회로 라우팅). 이 메트릭은 pickModel 재설계(Opus 유지) 이전에 쌓인 것으로 보입니다(추정: routing-redesign.md가 같은 날 변경됨). 재설계 이후에도 같은 현상이 있는지는 확인하지 못했습니다.

### 1-2. 전환 1회의 실측 비용·시간 (10-29 rotate 8건 + 10-28 route 2건)
- 소요 시간(rotate 시작~종료, 인계 노트 생성 턴 포함): Opus로 전환 11.7/14.0/16.2/18.3초(평균 약 15초), Sonnet으로 전환 21.0/21.8/22.1/23.1초(평균 약 22초). 사용자가 대기하는 시간입니다.
- 새 세션 첫 턴의 cache_creation: 22k~40k 토큰(표준 약 26k), cache_read 약 47k. 즉 전환마다 약 26k 토큰을 새로 캐시에 씁니다. 이전 세션에서 쌓은 캐시는 버려집니다.
- 분류기 호출: 캐시 적중 시 약 $0.008, 호출 15회 합계 $0.197(턴 비용의 약 1%). 전환 비용에서는 무시할 수준입니다.
- 인계 노트 생성 턴의 토큰/비용은 따로 기록된 필드가 없어 확인하지 못했습니다.

### 1-3. 캐시 가격 구조 (가정, 공식 확인 안 함)
- 아래 단가는 제가 알고 있는 공개 가격표(100만 토큰당)이며 이 세션에서 웹으로 재확인하지 않았습니다. usage-analysis.md에도 "모델별 단가 미확인"이라 적혀 있습니다.
  - Opus(4.5 이후 계열 가정): 입력 $5, 출력 $25, 캐시 쓰기(5분) $6.25, 캐시 읽기 $0.50
  - Sonnet: 입력 $3, 출력 $15, 캐시 쓰기 $3.75, 캐시 읽기 $0.30
  - Haiku: 입력 $1, 출력 $5, 캐시 쓰기 $1.25, 캐시 읽기 $0.10
- 캐시 읽기는 쓰기의 약 1/12.5(0.1배 대 1.25배)입니다. 캐시는 모델별로 따로 있어 모델 간 공유되지 않는다고 알고 있습니다(공식 문서 재확인 안 함). 이 점이 전환 비용의 핵심입니다.
- 검산: 위 단가로 10-29 단일 턴을 재계산하면 Sonnet 0.2427 턴은 약 $0.13, Opus 0.3362 턴은 약 $0.22로, 메트릭 cost_usd(각 $0.243, $0.336)보다 낮습니다. 차이는 서브에이전트 비용 포함, 또는 단가 가정 오류일 수 있고 어느 쪽인지 확정하지 못했습니다. 따라서 아래 달러는 "자릿수" 수준으로만 보시기 바랍니다.

## 2. 비교
### A. 메인 유지 + 서브에이전트 분산
- 장점: 메인 캐시가 유지됩니다(턴당 캐시 읽기 단가만). 전환 대기 15~22초가 없습니다. 작은 작업의 출력·탐색 토큰은 싼 모델에서 처리되고, 메인 컨텍스트가 커지지 않습니다.
- 단점: 서브에이전트마다 새 컨텍스트라 브리프 작성과 캐시 쓰기가 듭니다(서브에이전트 호출당 cache_creation 대략 3천 토큰 안팎: 10-29 sonnet 서브 94호출 287k/94, 트랜스크립트 기준). Opus가 힌트를 무시하면 효과가 없습니다. 지금 데이터에서 Haiku 호출은 8회뿐이고, Sonnet 메인이 Opus 서브를 55회 쓴 세션(d4657cd7)이 있어 위임 방향이 역행한 사례가 있습니다.

### B. 메인 세션 모델 전환(현재 코드의 rotate 방식)
- 장점: 작은 작업이 계속될 때 메인 단가가 낮습니다(Sonnet 출력 $15 대 Opus $25, 가정).
- 단점(실측): 전환 1회에 11.7~23초 지연, 새 세션 캐시 쓰기 약 26k 토큰, 인계 노트 생성 턴 1회, 인계 요약으로 인한 맥락 손실 위험이 있습니다. 작업이 끝나 돌아올 때 같은 비용을 한 번 더 냅니다(10-29는 8번 왕복).
- 전환 1회 비용 추정(가정 단가): 새 세션 캐시 쓰기 26k x $6.25/M = Opus $0.16, x $3.75/M = Sonnet $0.10. 인계 턴과 분류기를 더해 대략 $0.15~0.25. 왕복이면 약 $0.3~0.5. 시간은 왕복 약 37초(15+22). 10-29의 전환 후 턴 중 Sonnet 턴 비용이 $0.13~0.31이었으므로, 전환 비용이 그 턴 자체와 비슷하거나 큽니다.

### C. "같은 세션에서 /model로 전환(교체 없이)" — 코드에 없는 대안, 참고용
- 캐시가 모델별이라면 전환 직후 전체 컨텍스트를 새 모델 가격으로 캐시에 다시 써야 합니다. 40k면 Opus 기준 약 $0.25, 270k면 약 $1.7(가정 단가)로, 컨텍스트에 비례합니다. 이어서 컨텍스트가 압축 없이 이어지므로 맥락 손실은 없습니다.
- 현재의 rotate 방식은 크기를 약 26k + 인계 노트로 줄이므로, 컨텍스트가 큰 구간(100k 이상)에서는 오히려 rotate가 싸고, 40k 근처에서는 거의 차이가 없습니다(교차점은 가정 단가 기준 추정이며 실측하지 않았습니다).
- 이 방식이 실제로 지원되는지, 어떤 방식으로 재처리되는지는 코드와 문서에서 확인하지 못했습니다.

## 3. 권장안
1. 기본 Opus 유지 + 작은·무관 작업은 서브에이전트 위임(현재 pickModel). 전환은 사용자가 모델을 강제한 경우 또는 새 주제 + 큰 작업일 때만.
2. 전환 최소화를 위해 같은 모델 구간이 짧으면(예: 직전 전환 후 2~3턴 이내) 전환을 보류하는 히스테리시스를 고려할 만합니다(제안, 미구현·미검증).
3. 확인할 것: 재설계 후 실제 세션에서 route 전환이 줄었는지, Opus가 `[routing:]` 힌트를 따르는지(서브에이전트 호출 모델 분포를 다시 집계).
4. Sonnet 메인이 Opus 서브를 부르는 역행 방지(CLAUDE.md 규칙 또는 훅)가 필요합니다. 데이터상 d4657cd7 한 세션에서 55회였습니다.

## 4. 확인하지 못한 것
- 모델별 최신 단가와 캐시 모델 간 비공유 여부(공식 재확인 안 함; 위 단가는 가정).
- 인계 노트 생성 턴의 토큰·달러(필드 없음), 재설계 후 데이터, 분류기가 실제 사용한 모델.
- cost_usd가 서브에이전트 비용을 포함하는지(검산 불일치로 보아 포함 가능성이 있으나 확정 못함).
- 교체 직후 요약 손실로 인한 품질 저하(측정 수단 없음).
