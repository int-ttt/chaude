## 2. 원인 가설 (추정, 검증 필요)
- H1 (사실+추정): route-* 회전이 10분 안에 5회 몰림(00:07~00:15). 회전마다 새 세션이 시스템 프롬프트/핸드오프를 cache create로 다시 쓰며 2.2만~3.7만 토큰. 원인은 회전 자체가 아니라 "모델 전환 시마다 세션을 닫는" 정책일 가능성(추정). 규모: 11회전 약 30만 cache_create. 금액으로는 소액(해당 시간대 비용 약 7 USD).
- H2 (추정): 폭증의 금액 대부분은 cache_create가 아니라 대형 컨텍스트(ctx 약 27만)에서 턴마다 cache_read 약 130만 토큰을 읽는 비용. UTC 10-11시 229 USD 규모가 이에 해당. 즉 임계 270k는 Opus/Sonnet 기준인데 haiku 턴이 ctx 271531에 도달(line 358)하는 것은 임계 적용 오류 또는 회전 실패(12:31, 12:43 drained/closed F, 시도 2)로 지연됐을 가능성.
- H3 (추정): 회전 직후 첫 턴 cache 소실. 캐시 TTL이 5분(290초 idle)이면 회전 직후 새 세션은 prefix 캐시를 못 쓰고 2만~4.5만 create.
- H4 (추정): null 비용 턴 23건은 300초 타임아웃으로 비용 미기록 → 실제 사용량이 집계보다 큼(과소계상). 구간 내 3건.
- H5 (미확정): Task 하위 에이전트 토큰이 metrics에 안 잡힘. 현재 근거는 "별도 키 없음"뿐.

## 4. 해결 후보와 근거
- S1 라우팅 회전 축소: route-* 시 세션을 닫지 않고 모델별 live child를 유지/재사용(0.8.0 per-model live children와 연결). 근거: H1, 10분 5회 회전, 회전당 2.2만~3.7만 create. 기대: 해당 구간 cache_create 약 30만 감소(약 1 USD대, 금액 효과는 작음, 한도 소진 속도에는 영향 가능). 위험: 컨텍스트 오염, 모델 간 상태 불일치.
- S2 회전 임계/쿨다운 조정: route 회전에 최소 간격(예: 5분 이내 재회전 금지) 추가, haiku 임계 80k 유지 여부 재검토, ctx 회전 실패 시 재시도 간격/상한 점검. 근거: H2, line 358 및 11.9 USD 턴 반복. 기대: ctx 27만에서 턴당 약 12 USD 억제. 위험: 임계를 낮추면 회전이 늘어 H1 비용 증가(트레이드오프: 회전 1회 약 0.3 USD vs 대형 컨텍스트 턴당 약 12 USD로 대형 컨텍스트 억제가 유리하다는 비교는 추정).
- S3 집계 누락 수정(관측): (a) 타임아웃 턴에 cost null 대신 직전 누적/추정치와 timeout 플래그 기록, (b) 하위 에이전트 usage가 부모에 미포함이면 별도 키 기록, (c) metricscmd에 null 건수 표시. 근거: H4, H5. 이 단계는 사용량을 줄이지 않고 측정을 정확히 함.
- S4 타임아웃(300초) 처리 재검토: 타임아웃 후 재시도가 같은 큰 컨텍스트를 다시 읽는지 확인. 근거: null 23건 중 상당수가 haiku ctx 약 5만.
- S5 예산 상한 활성화(--task-budget-usd): 기본 꺼짐. 폭증 시 자동 중단. 근거: budget.go. 위험: 업무 중단. 값은 사용자 결정 필요.
- S6 TTL 설정 점검: CacheTTL auto/1h/5m 중 현재 값 확인. 1h면 idle 회전 3599초라 H3 영향이 작음(추정).
우선순위 제안: 검증 3~6 결과 후 S2 → S3 → S1 순(금액 영향 큰 순). 순서는 검증 결과로 바뀔 수 있음.
