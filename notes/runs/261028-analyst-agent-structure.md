# 에이전트 운영 구조 분석: A안 vs B안 vs 혼합안

범위: 분석만 했고 코드는 바꾸지 않았습니다. 근거는 CLAUDE.md 라우팅 줄, .claude/agents/*.md 프런트매터(haiku-coder: autoCompactWindow 100000, omitClaudeMd: true), DECISIONS.md, 이 세션의 경험입니다. 아래에서 추정은 "추정"으로 표시했습니다.

## 1. 현재 상태 (근거)
- 라우팅은 CLAUDE.md 7행에 정책으로 있습니다. 메인(Opus)이 듣고 라우팅하고, 하위 에이전트가 작업합니다.
- 15행에 이미 "같은 haiku-drafter/haiku-coder를 워크스트림마다 이어 쓴다"는 규칙이 있습니다. 즉 B안의 일부는 이미 정책입니다.
- 에이전트마다 autoCompactWindow가 있어(haiku-coder 100k) 누적 컨텍스트는 자동 압축으로 상한이 걸립니다.
- 에이전트 정의는 파일(.claude/agents)로 정적입니다. "사전 생성"은 새 파일 작성이 아니라 호출 시점에 세션이 만들어지는 것입니다.

## 2. 비교
| 항목 | A안 (Sonnet 디스패처가 분석·사전 생성·역할 부여·유지/폐기) | B안 (기능별 haiku 세션 영속, 닫고 resume) | 혼합안 |
|---|---|---|---|
| 토큰 비용 | 디스패처 호출이 매 요청에 추가됩니다(Sonnet 한 턴 + 브리핑 작성). 소규모 요청엔 순손해입니다 | 콜드 스타트 재브리핑을 줄입니다. 대신 누적 컨텍스트를 매 턴 다시 읽습니다. 프롬프트 캐시 TTL(기본 약 5분, 추정)이 지나면 캐시 읽기가 풀 입력으로 과금됩니다 | 짧은 워크스트림만 영속, 나머지는 일회성 |
| 품질 | 역할 부여가 정교해질 수 있으나, 디스패처가 맥락을 요약하면서 손실이 생깁니다 | 같은 파일·결정을 기억해 일관됩니다. 반면 오래되면 낡은 가정과 이전 지시가 오염원이 됩니다 | 워크스트림 경계를 명시해 오염을 제한 |
| 실패 위험 | 단일 장애점이 하나 늘어납니다. 디스패처가 틀리면 전체가 틀립니다 | 세션이 죽거나 압축되면 맥락이 사라집니다 | 위 둘의 중간 |
| 구현 난이도 | 높음. 폐기·유지 판단 로직과 추적 상태가 필요합니다 | 낮음~중간. SendMessage로 기존 에이전트를 이어가는 방식이 이미 있고, claude --resume도 있습니다 | 낮음~중간 |

## 3. 이번 세션의 실패 사례 (근거)
- 슬래시 명령 작업 중 "명령별 구현은 haiku-coder를 명령당 1개씩 병렬로 위임하라"는 지시가 이미 구현을 끝낸 뒤에 도착했습니다. 그래서 반영하지 못하고 "바꿀지 결정해 달라"고 되물었습니다.
- 교훈: 문제는 구조(A/B)보다 지시의 타이밍과 작업 단위 크기입니다. 이미 10개가 맵 한 줄씩인 작업은 위임 이득이 작았습니다. 사전 생성형(A안)이어도 늦은 지시는 해결되지 않습니다.
- 또 하나: 이 세션의 sonnet-analyst들은 샌드박스에서 ~/.claude 읽기·Write가 막혀 보고서를 못 남긴 경우가 여러 번 있었습니다(LEDGER). 에이전트를 영속시켜도 권한 문제는 남습니다.

## 4. 판단
A안의 "분석 후 사전 생성"은 이 하네스에서 효과가 작습니다. 에이전트 종류가 정적 파일 11개로 이미 고정돼 있어 "생성"이 사실상 선택 문제이고, 그 선택은 메인이 CLAUDE.md 7행 정책으로 이미 합니다. 별도 디스패처 호출은 매 요청에 Sonnet 한 턴을 더하는 고정비입니다(추정: 짧은 요청일수록 손해).
B안의 "지우지 말고 resume"은 CLAUDE.md 15행의 확장입니다. 비용 이득은 재브리핑 절감과 캐시 TTL 내 재사용에서 나오고, TTL이 지나면 줄어듭니다. 오염은 autoCompactWindow와 워크스트림 단위 폐기로 제어할 수 있습니다.

## 5. 추천 (1개): 혼합안 = B안을 기본으로, 유지/폐기 규칙만 명문화
디스패처는 새로 만들지 않고, 메인이 이미 하는 라우팅에 "유지/폐기" 판단을 붙입니다.
- 유지(같은 인스턴스 계속): 같은 워크스트림·같은 파일 집합이고, 직전 작업이 5분 안에 끝났거나 컨텍스트가 autoCompactWindow의 절반 미만일 때.
- 폐기(새로 시작): 워크스트림이 바뀌었거나, 사용자가 "아니…" 교정을 두 번 했거나, 결과가 오염된 것으로 보일 때, 또는 컨텍스트가 창의 대부분을 쓴 때.
- 복잡하거나 판단이 필요한 건 sonnet-analyst가 스코핑하고, 필요 시 ESCALATE로 opus-architect에 넘기는 현행 흐름을 유지합니다.

## 6. 구현 단계 (이후 작업, 이번에는 구현하지 않음)
1. CLAUDE.md 15행을 확장해 위 유지/폐기 규칙을 3~4줄로 명시합니다.
2. LEDGER 훅이 이미 에이전트 결과를 기록하므로, 에이전트별 마지막 작업 시각·워크스트림 이름 한 줄을 함께 남겨 "유지 가능" 판단 근거로 씁니다(훅 변경 필요, 소규모).
3. 메인이 후속 지시를 보낼 때 SendMessage로 기존 인스턴스를 이어가는지 확인하고, 실패(만료·종료)하면 새 인스턴스로 폴백하는 규칙을 둡니다.
4. 이 하네스의 Go REPL 세션 교체는 별개입니다. 그쪽은 임계값(300k) 기준 회전이고 하위 에이전트 영속과 무관하므로 건드리지 않습니다.
5. 2~3주 운영 후 LEDGER로 재브리핑 빈도와 오염 사례를 보고 임계값을 조정합니다.

## 7. 불확실한 점
- 프롬프트 캐시 TTL, 서브에이전트 resume의 정확한 제약(세션 만료, 도구 상태 보존)은 이번에 직접 측정하지 않았습니다. 구현 전에 작은 실험(같은 haiku-coder에 두 번 지시하고 토큰 사용량 비교)으로 확인하는 것이 안전합니다.
- 비용 수치는 측정값이 아니라 구조적 추정입니다.
