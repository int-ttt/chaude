# 프롬프트마다 Haiku 분류 vs 현재 sticky 계획 분석

date: 261029
근거: plan-three-session-structure-v2.md 4절(sticky: 새 세션 만들 때만 분류, 오분류 요약만 Opus 전달), analysis-opus-cache-tradeoff.md, analysis-usage-patterns-pre1027.md.
표기: "사실"은 위 문서에 적힌 값, "가정"은 저장소에 없는 값(단가, 분류 입력 크기, 프롬프트 수 추정 등).
단가는 저장소에 없습니다. 아래는 토큰 수와 상대 배율(캐시 읽기 0.1x, 가정)로만 비교합니다.

## 비용 비교
사실
- pre-10-26 패턴: cache_read 1,208,570,617 / assistant 레코드 2,799 = 호출당 약 43만 토큰(산술 결과). 계획의 "평균 400k"와 맞습니다. 단 토큰 합계가 중복 합산이면 과대일 수 있다고 원 분석이 적었습니다.
- 현재 계획은 분류를 새 세션 생성 때만 실행하고 이어지는 세션은 건너뜁니다(classify_skipped).

가정
- Haiku 분류 1회: 입력 약 2~4k(시스템 지시 + 새 프롬프트 + 짧은 요약), 출력 약 100. 캐시 없이 전부 새 입력으로 계산해도 약 3k.
- 비교 기준 1: 메인 세션 1회 호출 = 43만 토큰을 캐시 읽기(0.1x)로 읽음 = 입력 환산 약 4.3만. 분류 3k(1x, Haiku라서 실제 단가는 더 낮음) = 환산 약 3천 이하. 호출 1회 대비 약 7% 이하, Haiku 단가 할인을 반영하면 수 %.
- 비교 기준 2(프롬프트 단위): 프롬프트 1개가 메인 호출 여러 번을 만듭니다. 대략 tool_use 1,155건 / user 레코드 1,605건 중 도구 결과를 뺀 순수 프롬프트가 수백 건이라면(가정, 약 400~500건) 프롬프트당 메인 호출 약 6회(assistant 2,799 / 450). 프롬프트당 메인 비용 약 26만 환산 대비 분류 3천 = 1~2%.
- 결론(가정 기반): 분류 호출 자체의 비용은 메인 비용의 한 자릿수 % 이하입니다. 호출 비용만 보면 매 프롬프트 분류는 "싸서 문제 없다"입니다.

비용이 진짜 갈리는 곳은 호출이 아니라 호출이 일으키는 전환입니다
- 분류 결과가 다른 모델/세션이면 이동해야 합니다. 새 세션은 시작 컨텍스트(계획 모델 C0 30k)를 캐시 쓰기(2x, 가정)로 지불하고 핸드오프(output 5k, 출력 5x 가정)를 만듭니다. 환산 약 6만 + 2.5만 = 약 8.5만, 이는 400k 컨텍스트 메인 호출 2회분에 해당합니다.
- 기존 세션의 400k 캐시는 버려지거나(1시간 뒤 만료) 다른 모델로 이어 못 씁니다. 모델이 다르면 캐시를 공유하지 않습니다(가정).
- 따라서 매 프롬프트 분류의 총비용 = 분류 호출(작음) + 전환 횟수 x 약 8.5만(큼). 전환이 한 세션에서 몇 번 나느냐가 결정 요인입니다.

프롬프트 수 (축 2)
- 원 분석에는 프롬프트 수가 직접 없습니다. user 레코드 1,605는 도구 결과 레코드를 포함하므로 프롬프트 수가 아닙니다(미확인).
- 세션 7개, 장기 VocalAnalyze 4세션이 6,289 레코드. 세션당 프롬프트는 대형 세션에서 수십~백 단위(가정, 1,605~1,155 같은 차감이 불확실). 즉 대형 세션에서 매 프롬프트 분류는 세션당 수십~백 번 호출이고, 합계 비용은 작아도 건수는 많아 metrics 행이 같은 수만큼 늘어납니다.

## 정확도 비교
sticky (현재)
- 판단 시점: 세션 시작, 유휴 후 첫 프롬프트, 모델 지시, 카테고리 전환. 세션 중간에 일이 커지거나 작아져도 재판단하지 않음. 단 4가지 트리거가 중간 변화를 상당수 잡을 수 있음(가정).
- 오분류 비용 방향 1(작은 일로 보고 sonnet/haiku에 둠, 실제는 설계 필요): 설계 단계를 건너뜁니다. 실패 재시도 후 'opus로' 지시 또는 반복 실패 규칙(계획 4절)으로 뒤늦게 올라가며, 그동안의 호출이 낭비됩니다. 이 방향이 더 비쌉니다.
- 오분류 비용 방향 2(큰 일로 보고 opus에 둠, 실제는 작음): 단가 차이만큼 손해, 기능 손실은 없음.

per-prompt
- 이점: 세션 중간에 작업 크기가 변하면 즉시 반영. 설계가 필요해진 순간 잡을 수 있음.
- 한계: 중간 전환의 이득이 전환 비용(약 8.5만 환산)보다 커야 의미가 있음. 짧은 후속 프롬프트("응", "그걸로", 맞장구)는 이미 슬래시/맞장구로 건너뛰게 되어 있어 분류 대상이 아닙니다.
- 중간에 크기가 바뀌는 빈도는 저장소에 측정값이 없습니다(미확인). 이 분석의 최대 불확실성. pre-10-26 패턴은 Bash 93%의 실행/검증 반복이라 같은 일의 연속인 프롬프트가 많다고 추정(근거 약함).

분류 입력 범위 (축 5)
- 가능: 새 프롬프트 + 직전 분류 결과 + 한 줄 세션 요약(예: 현재 모델, 카테고리, 직전 작업 제목, 현재 ctx)만 넣으면 3k 수준입니다. 전체 컨텍스트를 넣을 필요는 없고 넣으면 40만 토큰이라 비용이 역전됩니다.
- 한계: 요약이 짧으면 "이어서 해줘" 같은 프롬프트의 실제 크기를 알 수 없음. 요약을 누가 갱신하는지(메인이 쓰는지, 하네스가 규칙으로 만드는지) 미정이며 이것이 정확도의 상한입니다.
- Opus 전달 방식: 현재 계획은 오분류 요약만 전달, 매 프롬프트를 Opus에 보내지 않음. per-prompt에서도 이 원칙은 유지 가능합니다.

## 가중치 방식의 추가 비용
- 프롬프트 토큰: 가중치 표(크기, 종류, 파일 수, 위험도, 반복 실패 가산 등)를 지시에 넣으면 분류 입력이 늘어납니다. 표 1k 추가 시(가정) 3k -> 4k, 호출당 약 +30%. 호출 비용이 작아 절대값은 미미하지만 per-action 점수 근거를 출력까지 요구하면 출력도 100 -> 300 정도로 늘어납니다(가정).
- 동기화 부담: 가중치 표는 모델 라우팅 규칙(opus/sonnet/haiku 기준), 270k/80k 한도, 재사용 우선 임계값(예 240k)과 같이 맞춰야 합니다. 현재 판정 로직은 classifier.go의 size/kind/worker + 'model:' 줄 + 대체 규칙입니다(계획 4절). 가중치가 이와 어긋나면 분류가 서로 다른 두 규칙으로 갈라집니다. 표를 바꿀 때마다 라우팅 코드와 테스트(conductor_test, classifier 테스트)가 같이 바뀌어야 합니다.
- 튜닝 불가능: 가중치를 맞추려면 정답 라벨(오분류 기록)이 필요한데 현재 하네스 metrics에는 pre-10-27 데이터가 0건입니다(원 분석). 가중치는 근거 없이 정한 값이 됩니다.
- metrics 부피: per-prompt는 classify 행이 프롬프트 수만큼, 가중치 방식은 행당 필드(항목별 점수)가 늘어납니다. 현재는 classify_skipped 한 줄로 충분합니다. 분석 비용이 아니라 해석 비용이 커집니다.
- 구현 범위: 계획의 구현 순서(1~4 haiku-coder 범위)에 per-prompt와 가중치를 더하면 4번(sticky)이 사라지고 대신 전환 규칙(전환 비용 대비 이득 비교)이 필요해 sonnet-analyst 범위로 올라갑니다(추정).

## 판정
- 매 프롬프트 Haiku 분류는 호출 비용 자체로는 부담이 작습니다(메인 호출의 수 % 이하, 가정). 그러나 그 이득을 실제로 얻으려면 세션 중간 전환이 필요하고, 전환은 호출 비용의 수십 배(약 8.5만 환산, 가정)이며 400k 캐시를 잃습니다.
- 따라서 per-prompt 분류는 "전환 없이 기록만" 하거나 "전환 비용을 계산해 이득이 클 때만 전환"하는 조건부일 때만 가치가 있습니다. 무조건 전환하는 per-prompt는 현재 sticky보다 비쌉니다.
- sticky가 이기는 조건: (a) 같은 세션 안에서 작업 크기가 자주 바뀌지 않음(Bash 중심 실행 반복 패턴), (b) 세션 컨텍스트가 커서 전환 시 잃는 캐시가 큼(평균 400k), (c) 4가지 트리거가 중간 변화를 대부분 잡음, (d) 가중치를 튜닝할 라벨이 아직 없음.
- 권고(가정 기반, 확정 아님): 현재 sticky 유지. 분류 호출은 건너뛰되 route-log에는 "무엇을 분류했을 것인가"를 건너뛴 프롬프트에 대해서도 샘플링해 남기는 것은 저렴(호출 3k)하므로, 샘플 오분류율이 측정되면 그때 per-prompt 도입 여부를 판단합니다. 가중치 방식은 라벨이 쌓이기 전에는 보류.

## 뒤집히는 가정
"한 세션 안에서 작업 크기가 자주(예: 세션당 3회 이상) 바뀌고, 크기를 잘못 잡았을 때 설계 단계 누락의 재작업 비용이 전환 비용(약 8.5만 환산)보다 크다."
- 이것이 참이면 per-prompt 분류와 전환이 이깁니다. 현재 저장소에는 세션 중 크기 변화 빈도 측정이 없어 확인할 수 없습니다.
- 확인 방법 한 가지: 위 샘플 기록으로 sticky가 건너뛴 프롬프트의 분류 결과와 현재 세션 모델의 불일치율을 며칠 쌓아 봅니다.
