# 계획: 상시 세션 8개를 실제 Claude Code 클라이언트 상태로 운용하는 환경 변인통제 방안

## 목표
- 사용자 확정 구성: 상시 세션 합계 8개 = 기본 4개(main opus · coder haiku · prompter haiku · tui haiku) + coder 여유 4개.
- 판단 대상: 이 8개를 claude code 클라이언트 실제 실행 상태(인터랙티브)로 돌려, "-p 사용량이 더 많다"는 관찰을 변인통제된 환경에서 확인하는 방안이 타당한지, 운용 트레이드오프는 무엇인지.

## 참고 사실 (출처)
- 현재 자식 세션: `claude -p --input-format stream-json` (core.go:145). 권한 control_request, task-notification 감지, usage/total_cost_usd, partial 스트리밍 모두 stream-json 의존 (261031-plan-interactive-child.md).
- 메인 기획서 판정(DECISIONS.md:47, 261031-plan-io-architecture-review.md): 인터랙티브 TUI 자식 반대, 상주 stream-json 자식 유지 권고. 브랜치명과의 충돌은 사용자 결정 대기.
- 유휴 회전 4m50s(DECISIONS.md:21). 실제 캐시 TTL 실측이 선행 조건.
- LESSONS.md:3: 회전 시 대기 중 import 스냅샷을 덮어쓰지 말 것.

## 핵심 쟁점: 무엇을 변인통제하는가
- 비교할 독립변수는 "클라이언트 모드(-p vs 인터랙티브)" 하나입니다.
- 통제할 나머지 변수: 모델, 시스템 프롬프트·도구 정의, CLAUDE.md·훅·--settings, 입력 프롬프트, 캐시 상태(콜드/웜), 동시 실행 부하, 측정 시점.
- 5시간 사용률·/usage는 계정 단위 집계로 보입니다(미확인 3). 그렇다면 8개가 동시에 돌 때 세션별·모드별 사용량을 분리할 수 없으므로, 8개 전부를 인터랙티브로 바꾸는 것은 오히려 변인통제를 어렵게 합니다.

## 방법 후보
A. 8개 전부 인터랙티브 PTY 클라이언트
- 장점: 실제 사용 환경과 동일, 모드 차이 자체가 사라짐.
- 단점: 구조화 신호 상실(권한, task-notification, usage), PTY 8개의 화면·대화상자 관리, 하네스 코드 경로 전면 재작성, 메인 기획서 판정과 정면 충돌. 계정 단위 계측이면 측정 귀속 문제는 그대로 남음.
B. 운영 8개는 상주 stream-json 유지 + 별도 A/B 측정 쌍(인터랙티브 1 · -p 1)
- 같은 모델(haiku)·같은 --settings·같은 고정 프롬프트 세트를 순차 실행하고, 측정 구간에는 운영 세션을 유휴 상태로 둡니다.
- 장점: 독립변수 1개만 변화, 운영 경로 무변경, 비용 작음.
- 단점: 인터랙티브 쪽 usage는 트랜스크립트 JSONL 또는 /usage 전후 차이로만 측정 가능(미확인 4), 실험용 스크립트 별도 필요.
C. 8개 전부 상주 stream-json, 측정은 usagepoll로만
- 장점: 추가 구현 최소.
- 단점: 모드 비교가 불가능해 사용자 질문에 답하지 못함.

## 권고
- B 채택을 권고드립니다. 이유: (1) 변인통제는 비교 실험에서만 필요하며 운영 8개를 바꿀 필요가 없음, (2) 계정 단위 계측에서 8개 동시 실행은 사용량 귀속을 불가능하게 함, (3) 메인 기획서 판정(stream-json 유지)과 일치.
- 8개 상시 구성 자체는 stream-json으로 수용합니다. coder 여유 4개는 "프로세스만 대기, 턴 미전송" 상태로 둡니다. 유휴 세션은 턴을 보내지 않으면 토큰을 쓰지 않는 것으로 보이나(미확인 6), 캐시는 TTL 경과 후 사라지므로 여유 세션의 이점은 기동 지연 절감뿐입니다. keepalive 핑은 비용이 생기므로 기본 off입니다.
- A는 B 결과에서 인터랙티브가 유의하게 적게 소모한다고 확인될 때에만 재검토합니다.

3. 측정 구간 동안 운영 8개 세션 턴 0 확인, usagepoll 기록 병행.
4. 결과를 notes/research/billing.md에 추가하고 DECISIONS.md에 채택 여부 기록.

## 엣지 케이스
- 측정 중 유휴 회전(4m50s) 발동 시 핸드오프 턴이 사용량을 오염 → 측정 구간 `--idle-rotate 0`.
- 인터랙티브 쪽 신뢰/온보딩 대화상자 → 사전 승인된 디렉터리에서 실행.
- 8개 동시 요청 시 429/동시성 제한 (261029-analysis-concurrency-limit.md 참조, 수치 미확인).
- tui 출력이 opus 입력으로 유입되지 않도록 격리 유지 (구현 경로 미확정).

## 미확인 항목 (12개)
1. -p 사용량이 구독 한도에 일반 대화와 같은 기준으로 계상되는지 (billing.md:18)
2. 인터랙티브와 -p의 시스템 프롬프트·도구 정의가 동일한지 (토큰 수·캐시 prefix 차이)
3. /usage·5시간 사용률이 계정 단위 집계인지, 세션 귀속이 가능한지
4. 인터랙티브 트랜스크립트 JSONL에 usage 필드가 기록되는지, 기록 시점
5. 실제 캐시 TTL (5분 vs 1시간)
6. 유휴 상주 프로세스가 토큰을 전혀 소모하지 않는지 (백그라운드 요청 여부)
7. 인터랙티브 프로세스 1개당 메모리·CPU, 8개 동시 부하
8. 계정 동시 요청 한도와 8개 동시 실행 시 429 빈도
9. PTY 인터랙티브에서 --settings 훅 실행·사용자 설정 병합
10. -p stream-json 모드에서 /clear가 슬래시 명령으로 처리되는지, 처리 후 prefix 캐시 재사용 여부
11. 유휴 상태에서 task-notification 전달 여부
12. tui 출력 격리 구현 경로
