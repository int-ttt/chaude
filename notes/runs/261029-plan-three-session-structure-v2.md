## 3. 세션 구성
- 상시 Opus 설계 세션 1개 + 실행 세션 동시 1~2개 (opus/sonnet 위주, haiku는 작은 조회용). 가정.
- [검토반영] 살아 있는 동안 캐시를 따뜻하게 유지하고, 컨텍스트 크기는 270k로 제한(세션별 적용).
- 같은 프로젝트 작업은 같은 실행 세션으로 보낸다 (캐시 재사용, 5절).
- [검토반영] Bash 위주 opus 실행 작업은 설계 세션이 아니라 별도 opus 실행 세션(sonnet 실행 세션과 같은 규칙)이 처리. 설계 세션은 설계 턴만 (DECISIONS:40(1)). 근거: opus-5가 주 실행자였고(output 1.22M, Bash 93%) Bash 출력이 270k를 빨리 채워 설계 맥락을 밀어냄. 이는 정정 2의 "opus 실행 세션" 선택지와 일치하며 v1 Q3 가정을 대체.
- 훅/카테고리 회전/답변 언어(한국어 존댓말) 규칙은 v1과 동일.

## 4. 분류자 흐름
- 분류자 출력: topic/size/kind/worker/task + `model: haiku|sonnet|opus` 줄 (v1과 동일). 라우팅: 작은 조회/수정 -> haiku / 검토·분석 -> sonnet / 설계·판단·반복 실패·'opus로' -> opus. model 줄 누락/무효 시 size/kind로 대체. 강제 --model 우선.
- [검토반영] 세션이 이어지면 프롬프트마다 분류 호출을 생략한다 (sticky). 생략 조건: 맞장구/슬래시, 또는 직전 턴이 1시간 안의 살아 있는 실행 세션이고 모델 지시('opus로' 등)와 cat 전환이 없음. 분류자는 새 세션을 만들 때만 실행: 유휴 종료/회전 후 첫 프롬프트, 모델 지시, cat 전환. metrics에 classify_skipped=true|false.
- [검토반영, 가정] 재사용 우선: 같은 모델 세션이 살아 있고 같은 cat/파일이며 ctx < 270k-여유(예: 240k)면 새 세션을 만들지 않는다. 여유 초과면 먼저 따뜻한 핸드오프로 회전 후 라우팅. 정정 2/3을 바꾸지 않는 기본 선호이며, 효과는 route-log 재사용률로 측정.
- 분류 입력/답변은 route-log 파일에 기록. Opus에는 프롬프트마다 보내지 않고 설계 턴에만 오분류 요약(모델별 건수, 사용자가 모델을 강제했거나 다른 모델로 재실행한 목록)만 전달. 정정 4의 "전달"은 파일에서 확인 가능으로 충족 (해석, 열린 질문 6).
- 분류 호출 1회, 도구 없음, metrics stage=classify.

## 5. 캐시 전략 (비용은 가정)
- 비용 추정은 가정이다. 단가(읽기 0.1x, 1시간 쓰기 2x, output 5x input)는 저장소에 없고 공식 가격 확인 필요 (열린 질문 2). 모델: C0 30k, g 15k/call, 핸드오프 output 5k.
- 호출당 비용(입력토큰 환산): R=150k 51.5k / 200k 50.8k / 270k 52.0k / 400k 56.6k / 무회전 평균 400k 약 70k. 150~270k에서 곡선이 평탄, 400k는 약 9% 비쌈. 그래서 270k를 유지한다. 평균 400k 컨텍스트가 한도가 중요한 이유다.
- 더 큰 비용 요인은 1시간 만료 후 재진입: C=400k에서 재쓰기 2x400k = 800k환산(약 15호출). 야간 집중 + 수일 공백 패턴(18일 활동/약 7주)이라 임계값보다 만료 재쓰기가 지배(추정).
- [검토반영] 기본 종료 동작은 59:59 핸드오프 (6절). DECISIONS:23과 정정 3 관계는 열린 질문 4.
- 설계 세션은 cache-tradeoff A안(상시 유지). 하이브리드는 정정 1 해석에 달림 (열린 질문 3).
- 설계 파일 `## decisions`/`## open` 절 제안 (열린 질문 8). 회전 직전 결정을 파일에 기록.

## 6. 유지/종료 규칙 [검토반영: DECISIONS:23에서 변경]
- 대상: 살아 있는 실행 세션. 설계 세션 제외.
- 1시간 안: 항상 유지 (유휴는 비용 0).
- 기본 종료 동작 = last_used+3570초(59:59)에 핸드오프: ctx >= 60k(가정)면 따뜻한 핸드오프(읽기 약 0.1C) 후 종료, 이후 첫 프롬프트는 스냅샷에서 새 세션. ctx < 60k면 결정론 스냅샷으로 종료(토큰 0, DECISIONS:19 옵션). 세션별 Opus 판단 호출 없음. 이는 DECISIONS:23의 변경이며 정정 3(Opus 유지/종료 판단)과의 관계는 사용자 결정(열린 질문 4).
- 핑(유지): 사용자 활동 시간대 안에서만, 최대 1회. 활동 시간대는 pre1027 기준 UTC 13-15 등(가정). 핑 비용 약 0.1C vs 재쓰기 2C -> 1시간 내 복귀확률 > 약 5%면 이득 (가정 배율). 구현은 과금 확인 후 마지막 (열린 질문 5).
- 파싱 불필요: Opus keep/end 출력과 "컨텍스트가 클수록 keep" 기울기는 제거.
- 종료 시 백그라운드 에이전트가 있으면 draining (DECISIONS:18). 구현 토대: parked + workerPool.

## 7. 컨텍스트 한도
- opus/sonnet 270k, haiku 80k (repl.go:26-27, :870) 유지. 세션별 적용. 도달 시 답변 후 rotate() + handoff, 백그라운드 에이전트 있으면 draining.
- 선택은 사용자 몫: DECISIONS:40(2)("컨텍스트 유지, 임계값 전환 없음") vs :41(270k/80k)이 충돌. 이 문서는 어느 쪽도 택하지 않음 (열린 질문 1). 연속성 선택 시 임계 350k + compact 창 500k 이상(1M 모델) 비용 약 +5% (Opus 검토).
- compact 창 400k (repl.go:871): Bash 위주 턴은 답변 한 번에 270k->400k 초과 가능(회전은 답변 후). 270k는 약 130k 여유. [검토반영] 턴당 ctx 증가(max, p95)를 metrics에 기록, p95 > 130k면 compact 창 상향(1M 모델 예: 600k) 또는 사전 회전(ctx >= 240k + exec이면 전송 전 회전).
- effectiveThreshold (repl.go:695)는 모델 단위. [검토반영] 세션별 구조체 {id, model, lastCtx, threshold, lastUsed, cat, files}를 두고 회전/종료가 이를 읽는다.
- 설계 세션 회전 핸드오프: 설계 파일 경로 목록 + 미결 항목.

## 8. 데이터 흐름 (설계 파일 기준 haiku-scout 호출)
- 설계 파일: `notes/runs/<YYMMDD>-plan-<topic>.md`, 필수 절 `## evidence`, `## brief` (haiku <=3,000자, sonnet <=6,000자), 제안 `## decisions`, `## open`.
- haiku-scout 호출: 호출 주체 Opus 설계 세션. 입력 = 설계 파일 절대경로 + 질문 1개. 출력 5줄 이하, 읽기 전용, 원문 붙여넣기 금지. `## evidence`에 없는 것만 조사.
- 실행 세션은 Opus 데이터를 직접 가져가지 않고, 설계 파일 완료(존재+size>0+2초 안정) 후 brief를 받아 시작. 작은 작업은 대기 없음. 결과는 notes/runs/에 쓰고 요약만 반환 (DECISIONS:36).
- [검토반영, 9절에서 이동] 정정 6(실행 세션은 Opus 데이터를 직접 안 가져감)과 서브에이전트(Agent/SendMessage) 위임 흐름의 충돌은 전제와 무관하게 설계에 영향. 정정 6의 적용 범위(실행 세션 시작 입력만인가, 하위 위임 포함인가)는 열린 질문 7. 가정, 미검증.
- 파일 소유자: 설계 파일=Opus, route-log=chaude, 결과 파일=실행 세션, metrics=chaude.

## 9. 10-27 이후 방식과의 차이 (위험 진술, 설계 목표 아님)
실측 (0901-1031 분석): 세션 169개(이전 6개), 호출당 cache_read 약 27k~64k(270k의 약 10~24%), Agent 370 / Handback 428, haiku-5-5 호출이 큼, harness 47.8%, 10-27~29 3일이 레코드의 82.6%.
작은 세션이 많은 방식에서 이 구조가 겪을 수 있는 것:
1. 세션마다 새 캐시 쓰기가 발생해 재사용 이득이 줄어든다.
2. 설계 호출이 드물면 상시 Opus 세션이 고정비로 남는다 (cache-tradeoff 조건 2, 4).
3. 살아 있는 세션 수가 많으면 종료 처리와 상태 관리가 늘고 현재 코드는 모델 하나만 본다.
4. 설계 파일/route-log 쓰기와 Opus 읽기 비용이 늘고 설계 파일 드리프트(W10)가 심해진다.
근거 한계: 3일 데이터, 하네스 개발 작업에 치우침. 10-29는 부분 일, 10-28이 22,084건으로 일자 불균형. 호출당 27~64k는 haiku/sonnet/opus-5-5 모델 혼합이라 "세션이 작아짐"과 "모델이 달라짐"이 분리되지 않음. 일반 패턴이라 단정 불가.
