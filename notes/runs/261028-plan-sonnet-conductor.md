## 1. 메인 모델을 Sonnet으로, 위임 분류 기준
현재: 메인은 Opus이고 도구 없이 듣고 라우팅만 합니다(CLAUDE.md). 변경안: 메인을 Sonnet으로 두고 같은 라우팅을 맡깁니다. 이유는 메인이 매 턴 전체 컨텍스트를 다시 읽는 고정비라 가장 비싼 모델일수록 손해이기 때문입니다(추정, 4번 실험으로 확인).

분류 기준(메인이 위임 시 적용):
| 등급 | 담당 | 조건 |
|---|---|---|
| 기계적 | haiku-* | 바꿀 정확한 텍스트가 이미 정해진 편집, 변환, 검색, 실행/모니터링, 웹 조회 |
| 판단 | sonnet-analyst | 무엇을 바꿀지 정해야 하는 다중 파일 편집, 진단, 설계 판단, 종합, 긴 문서 |

- 메인이 Opus일 때 "Opus가 Opus에게 위임하면 이득 없음"이던 규칙은 Sonnet 메인에서는 opus-architect 위임이 실제 상향이므로 완화될 수 있습니다. CLAUDE.md 문구 수정 필요.

## 2. 에이전트 수명
- 유지: 같은 workstream이면 같은 에이전트를 SendMessage로 resume. 현행 "haiku-drafter/haiku-coder 이어쓰기"를 sonnet-analyst까지 확장합니다.
- 폐기(새로 시작): workstream 변경, 같은 에이전트에서 반복 실패(교정 2회 또는 실패 2회), 컨텍스트 과대(autoCompactWindow의 대부분 사용, 이전 분석 기준: 절반 미만이면 유지).
- 작업 방식은 첫 브리프에 명시: 산출물 경로, 검증 방법(acceptance), 반환 형식(≤5줄), 이후 같은 workstream 지시가 이어진다는 점. 후속 지시는 교정 원문 + 1줄만.
- resume 실패(만료/종료) 시 새 인스턴스로 폴백하고 첫 브리프를 다시 보냅니다.
- 추적: 메인이 workstream 이름 → 에이전트 ID → 마지막 작업을 한 줄로 유지(3번의 위임 상태와 같은 정보).

## 3. 세션 교체 변경
현재(repl.go): 컨텍스트가 300k를 넘으면 rotate. handoffPrompt로 인계 노트를 받고(목표, 결정, 변경 파일, 진행 중, 열린 질문, 사용자 선호, 정확한 코드/숫자), buildSnapshot이 노트 + 변경 파일 + 최근 4턴(각 1500자 절단)을 합쳐 24,000자로 자릅니다. 단일 임계값이라 교체 시점에 실행 중인 위임을 고려하지 않습니다.

변경안(사용자 결정 261028: "최대 상한은 없애자. 그리고 매 답변 후마다 현재 컨텍스트 크기가 270k 이상이면 다음 세션을 전환 작업을 수행하도록 하자"): 단일 규칙.
- 매 답변이 끝난 직후 ctx >= 270000이면 인계 후 새 세션으로 전환. `--threshold` 기본 270000, 하드 상한(300k)과 준비 단계(`--prep-threshold`)와 `--max-auto-rotations`는 두지 않음. 비교는 `>=`.
- 에이전트 대기 중 빠른 전환(사용자 추가: "만약 에이전트 대기중이라면 빠르게 전환하는 방법도 있지"): 270k에 도달했는데 백그라운드 에이전트가 실행 중이고 메인은 완료만 기다리는 상태이면, 끝나기를 기다리지 않고 즉시 전환. 인계에 실행 중 에이전트의 ID, 맡긴 일, 출력 경로를 기록하고, 완료 알림은 새 세션으로 전달하거나 새 세션이 resume하도록 함.
- 실패 안전: 인계 노트가 비거나 실패하면 결정적 스냅샷으로 폴백하고, 연속 재시도 폭주를 막는 쿨다운을 둠(상한을 없앴으므로 필요). 자세한 내용은 notes/runs/261028-longsession-improvements.md.
- compact-window(400k)는 threshold보다 커야 한다는 기존 제약 유지.

### 3-1. 이전 프로세스 유지(드레인) 방식 (사용자 확정 261028: "이전 프로세스를 끝내지 않는 방식. 에이전트가 끝날 때까지 백그라운드로 남겨 두고, 결과 파일이 생기면 새 세션에 알려 줍니다. 이게 맞는것같다")
이 방식이 위 "즉시 전환"의 완료 처리 방법이며, (A) resume 경로 대신 이것을 채택. 교체 시 에이전트가 실행 중이면 이전 child를 Close하지 않고 드레인 목록으로 옮김.
- 구조: Repl에 `draining []*drain` 추가. drain = {sess *Session, agents map[agentID]{task, outPath, startedAt, done}, since}. rotate()는 실행 중 에이전트가 없으면 기존처럼 Close, 있으면 sess를 draining에 넣고 새 세션만 시작(repl.go:319 `r.sess.Close()` 분기).
- 실행 중 에이전트 수집: runTurn의 handle에서 `tool_use`(name Agent/Task)의 id와 input(description, prompt의 산출물 경로, run_in_background)을 기록하고, 대응 `tool_result`가 오면 완료 처리. 백그라운드 에이전트의 agentId와 출력 파일 경로가 tool_result에 들어오는지는 미확인 -> 실험 1에서 확인. 경로가 구조화되어 있지 않으면 브리프의 `notes/runs/...` 경로를 정규식으로 추출하고, 인계 노트의 Delegations 섹션이 같은 경로를 쓰게 함.
- 완료 감지(우선순위 순, 둘 중 하나면 완료):
  1. 파일: 각 에이전트의 결과 경로가 존재하고 크기가 0보다 크며 2초 이상 변하지 않음(하네스가 2초 간격으로 stat 폴링). SubagentStop 훅이 notes/LEDGER.md에 줄을 붙이므로(ledger.py), LEDGER의 새 줄을 보조 신호로 사용. 단 현재 LEDGER 줄에는 agentId가 없어 매칭이 불가하므로 ledger.py가 agent_id와 transcript 경로를 같이 쓰도록 수정 필요.
  2. 이벤트: 드레인 중에도 이전 sess.lines를 계속 읽는 고루틴을 두고, 그 프로세스가 내는 완료 알림/`result` 이벤트로 해당 에이전트를 완료 처리(이벤트 형식은 미확인).
  - 안전 타임아웃: drain 시작 후 N분(기본 60분, 플래그) 또는 마지막 이벤트/파일 변화 후 idle 10분이면 미완료로 표시하고 종료 단계로 진행(무한 유지 방지).
- 종료 절차(모든 추적 에이전트가 완료/타임아웃 후): (1) 이전 프로세스가 아직 응답 중이면 최대 30초 대기하며 이벤트를 읽어 버림(무시하되 transcript에 kind=drain으로 기록), (2) `sess.Close()`(stdin 닫기 -> 최대 15초 대기 후 Kill, core.go:204-214), (3) draining에서 제거. 하네스 종료(/quit, 신호) 시에는 모든 drain을 같은 절차로 즉시 종료(남은 에이전트는 미완료로 새 세션 인계 기록 없이 transcript에만 남김).
- 새 세션 통지: 완료 시 `[agent done] ID · 일 · 결과 경로 · 완료/타임아웃` 줄을 큐(pendingNotices)에 넣고, 사용자의 다음 입력 앞에 pendingSnapshot과 같은 방식으로 붙임(repl.go:342-345). 새 세션 턴 중간에는 주입하지 않음. 상태줄에 "에이전트 N개 대기" 표시, 사용자 입력이 오랫동안 없으면 알림만 화면에 표시(새 세션에 자동 턴을 보내지 않아 270k 재독 비용 없음).
- 이전 프로세스 처리 규칙: 드레인 중인 child의 `control_request`(권한 요청)는 자동 거부로 응답하고 기록(사용자 입력을 받을 수 없음). 이전 프로세스가 완료 알림을 받아 스스로 새 턴을 시작하면(모델 호출 발생, 270k 재독 비용 [추정]) 출력은 화면에 보이지 않고 transcript에만 기록. 이 추가 턴의 비용 크기는 실험 1에서 측정.
- 비용/리스크: 드레인 중 이전 프로세스 메모리, 출력 파일 폴링, 5h 사용량에는 에이전트 작업 토큰만 추가(이전 세션 재독은 알림으로 깨어나는 경우에만). 동시 드레인 수 상한(기본 3)을 넘으면 가장 오래된 것부터 종료 절차 적용.
- 확인 필요: (a) 에이전트 tool_result/이벤트에 agentId와 출력 경로가 있는가, (b) 백그라운드 완료가 stream-json에서 어떤 이벤트로 오는가, (c) stdin을 닫지 않고 두면 child가 계속 에이전트를 돌리는가(-p 모드 child가 입력 대기 중 백그라운드 에이전트를 계속 실행하는지 [미확인]), (d) 알림으로 깨어난 이전 child의 추가 턴 비용.

### 3-2. 4분50초 무입력 강제 정리 (261028 변경: 15분 -> 4:50) (사용자 확정 261028: "15분 이상 입력(키보드 입력을 포함한 모든 인풋)을 안하면 강제 세션 초기화(다음 세션으로 넘길 데이터만 정리)를 수행해. 이후 다음 프롬프트가 입력되면 다음 세션에게 해당 세션 정리치를 먼저 넣은 뒤 프롬프트 입력해서 해.")
- 기준 시계: TUI 입력 타이머. 현재 tui.go에는 유휴 타이머가 없음 [사실: grep 결과 rotate/threshold만 있음]. bubbletea `tea.Tick`(예: 30초 간격)으로 `lastInput`을 비교. 갱신 대상: KeyMsg(붙여넣기 포함), 마우스 클릭/휠(모션만 있는 이동은 제외 권장: 셀 모션 이벤트가 잦아 타이머가 영원히 리셋됨 [추정, 사용자의 "모든 인풋"과 해석 차이 있음, 확인 필요]). 에이전트 완료 알림, 스트리밍 출력은 입력이 아님.
- 타이머 정지: 턴 진행 중(runTurn)과 권한 프롬프트 응답 대기 중에는 세지 않고, 턴이 끝난 시각 또는 마지막 입력 중 늦은 쪽부터 4분50초를 셈. 4분50초 넘는 위임 턴이 끝나자마자 교체되는 일을 막음.
- 동작: 4분50초(기본 `--idle-rotate 290s`, 0이면 끔) 경과 시 rotate("idle 4m50s")를 실행(인계 노트 -> 스냅샷 -> 새 세션 시작, 새 세션에는 아직 아무것도 보내지 않음). 스냅샷은 pendingSnapshot에 두고 다음 프롬프트 입력 때 `스냅샷 + (대기 알림) + 현재 프롬프트` 순서로 합쳐 보냄(repl.go:342-345 기존 경로). 마지막 교체 이후 턴이 없으면(이미 새 세션) 건너뜀. 안전장치(3번 개선안 1: 노트 검증/폴백/쿨다운)와 드레인(3-1) 그대로 적용.
- 비용(변경): 사용자 변경 261028 "캐시 만료가 5분이라면 그냥 5분으로 하자 4:50초". 캐시 TTL(약 5분 [추정, 미측정]) 안에서 교체하므로 인계 턴이 캐시가 유효한 컨텍스트를 읽어 cache-read 단가로 청구됨(15분안의 캐시 재생성 비용이 사라짐). 이후 새 세션 첫 프롬프트는 새로 시작하는 작은 컨텍스트라 캐시 생성은 작음. 인계 턴 출력 토큰은 별도. 옵션(결정적 스냅샷, 0 토큰)은 유지.
- 위험 1: 교체가 더 자주 일어남. 5분 미만 간격 사용 중에는 타이머가 안 걸리지만, 생각하는 시간이 5분 가까운 작업에서는 매번 교체되어 인계 품질 손실(뉘앙스, 교정 이력)과 인계 턴 비용이 누적됨. 완화: 직전 교체 이후 턴 수가 적으면 건너뜀(최소 N턴), 쿨다운, 컨텍스트가 작으면 결정적 스냅샷.
- 위험 2: TTL이 실제로 5분이 아닐 수 있음(예: 1시간 TTL 또는 구독 등급별 차이). 그러면 290초 교체는 캐시가 한참 유효한데 불필요하게 교체하는 것이 되어 이득 없이 연속성만 손실. 따라서 TTL 실측(같은 접두부로 간격 60/240/290/330/600초 후 usage의 cache_read/cache_creation 비교)을 구현 선행 조건으로 함. 실측 결과로 `--idle-rotate` 기본값을 정함.
- 설정: `--idle-rotate <duration>` 플래그(기본 290s, 0 = 끔)로 조정 가능.
- 드레인과의 관계: 15분 시점에 에이전트가 실행 중이면 3-1 절차 그대로(이전 child 유지, 새 세션 시작). 4분50초 타이머는 새 세션 기준으로 다시 시작하며 에이전트 완료 알림은 타이머를 리셋하지 않음. 완료 알림은 다음 프롬프트 앞에 스냅샷 다음 순서로 붙음. 드레인 child가 있어도 유휴 교체가 가능하며 드레인 수 상한(3)은 공통.
- 사용자 경험: 교체 시 상태줄/알림에 "유휴 정리됨" 한 줄만 표시(대화 화면을 비우지 않음). 사용자가 돌아와 입력하면 첫 응답은 새 세션의 첫 턴이라 캐시 생성이 한 번 있음.

- TTL 확정 갱신(261028, 근거 notes/runs/261028-cache-ttl.md 4a/4c/5a/5g, 공식 문서): 구독 플랜 내 메인 대화는 1h, 초과(usage credits)·API key는 메인도 5m. `CLAUDE_CODE_PROMPT_CACHE_TTL=1h`(v2.1.242+)로 고정 가능. 따라서 위 "5분/290초" 가정은 구독 기본값에서는 틀림 [사실]. 사용자 결정 261028: "그럼 캐시 갱신은 59:59초에 수행하게 하고": TTL을 1h로 핀하고 만료 직전에 유휴 인계 실행.
  - 기본값: `--idle-rotate` 3599s(사용자 지정 59:59). 권고: 1초 여유는 요청 지연과 시계 오차로 경계를 넘길 수 있음(인계 턴이 만료된 캐시에서 시작하면 1h 쓰기 2x 단가로 재생성) -> 약 59:30(3570s)을 권장 [추정]. 타이머 기준은 "마지막 API 요청 시각"(캐시 갱신 시점)이지 마지막 키 입력이 아님에 주의: 입력이 없어도 에이전트 완료로 child가 요청을 보냈으면 TTL이 갱신되므로 타이머을 마지막 요청 시각 기준으로 두는 것이 정확 [추정, 사용자 문구는 "입력 기준"].
  - 비용: 1h 캐시 쓰기는 2x 단가(5m은 1.25x). 인계 턴은 캐시가 유효한 컨텍스트를 읽으므로 cache-read 단가. 이후 새 세션 첫 턴의 쓰기는 작음.
  - 위험 3: 초과 사용으로 메인이 5m로 떨어짐(4c). 이때 3570s 타이머는 이미 만료 후라 인계 턴이 캐시 재생성 비용을 냄. 대응: 환경변수로 1h 고정(초과 시 1h 쓰기 단가 지불), 시작 시 `claude -p "hello" --output-format json`의 usage.cache_creation(ephemeral_1h/5m)으로 실제 TTL 검증(5g), 각 턴 usage에서 5m 쓰기가 보이면 타이머를 290s로 자동 하향. 2번 위험(TTL 오인)은 공식 문서로 대부분 해소되었으나 환경별 실측은 여전히 선행 조건.
  - 위험 1(교체 빈도)은 59분 기준에서 크게 줄어듦.

인계 내용에 추가:

- 위임 상태: 에이전트 ID, 맡긴 일, 결과 경로, 완료/진행 중 여부. handoffPrompt에 "Delegations: agent ID · task · result path · status" 섹션을 추가합니다.

## 4. 검증 실험: Sonnet 메인 vs Opus 메인
설계: 같은 시나리오 스크립트(약 15~20턴)를 두 메인으로 각각 실행. 시나리오에는 (a) 단순 요청, (b) 위임이 필요한 다중 파일 작업, (c) 사용자의 정정("아니…"), (d) 사용자의 반박(사실과 다른 주장), (e) 모호한 요청이 섞입니다.
측정:
- 토큰/비용: 메인 입력·출력·캐시 토큰, 총 비용(usage 줄 값), 하위 에이전트 포함 합계.
- 정정 처리: 정정 원문을 정확히 중계했는가, 같은 실수를 반복했는가(반복 횟수).
- 반박 처리: 근거 없는 반박에 동조했는가, 근거로 답했는가(수동 채점 0/1, 2인 이상 또는 sonnet-reviewer).
- 라우팅 정확도: 분류 기준(1번)과의 일치율.
판정 기준(초안): Sonnet 메인이 총비용 ≥30% 낮고, 정정 반복·반박 동조가 Opus 이하 수준이면 채택. 아니면 Opus 유지(또는 반박·모호 요청만 opus 위임). 표본이 작아 통계적 결론은 불가(추정: 1회 실행의 편차 큼) — 시나리오당 2회 이상 권장.

## 4-b. 검토 항목: 무상태(stateless) 지휘 Sonnet (사용자 요청 261028, 미검증)
- 아이디어: 입력마다 지휘 Sonnet 세션을 초기화하고, 작은 상태 주입만 받음. 주입 내용: 마지막 `추천:` 원문, 열린 workstream(목표/다음 행동/에이전트 ID와 결과 경로), 최근 2턴. 코드가 transcript.jsonl과 LEDGER에서 결정적으로 만들 수 있어 인계 모델 호출이 없음 [추정].
- 토큰 비교(추정, 미측정): 상주형은 매 턴 컨텍스트 전체를 cache read(싸지만 컨텍스트에 비례, 평균 약 135k~270k)하고 270k마다 인계 턴 1회. 무상태형은 매 턴 시스템 프롬프트+CLAUDE.md+상태(약 수 k 토큰)만 입력하고 캐시 접두부(정적 부분)는 TTL 안에서 재사용 가능하나 상태 부분은 매번 새로 생성. 입력 간격이 캐시 TTL보다 길면 상주형도 어차피 재생성이므로 무상태형 이득이 큼. 이어서 말하는 연속 입력(몇 초 간격)에서는 상주형의 cache read가 더 쌀 수도 있음. 프로세스 시작 지연(턴마다 child 기동 수 초 [미측정])이 단점.
- 연속성 비교(추정): 상주형은 교정 이력, 사용자의 뉘앙스, 방금 본 도구 결과를 유지. 무상태형은 "ㅇㅇ"는 `추천:`로, 위임 결과는 notes 경로로 이어지지만 "아까 그거"처럼 최근 2턴 밖의 지시어, 같은 항목 2회 교정 이력(CLAUDE.md의 교정 규칙), 말투 적응이 끊길 위험. 정리 상태의 품질이 전부 코드와 notes 규율에 의존함.
- 사용자 제안(261028, 4-b 구체화): "커맨더에게 최근 5 프롬프트와 답변, 전체 프로그레스를 요약한 정보를 넘겨주면 되는거 아닐까?" + "조사와 요약은 haiku로만 처리하게".
  - 입력마다 지휘자에게 주는 것 3가지: (1) 최근 5개 프롬프트/답변 쌍, (2) 직전 답변의 `추천:` 전문(절대 자르지 않음), (3) 전체 프로그레스 요약. 지휘자는 원자료(transcript, notes)를 다시 읽지 않음.
  - 수집/요약 담당은 Haiku만(지휘자 아님). 프로그레스 요약은 매번 재생성하지 않고 턴 종료 후 증분 갱신: 직전 요약 + 방금 턴(프롬프트, 답변, 위임 결과) -> 새 요약, 결과를 notes(LEDGER/PROGRESS 파일)에 저장. 최근 5쌍과 `추천:` 전문은 요약 없이 코드가 transcript.jsonl에서 결정적으로 추출(Haiku 불필요).
  - 길이 정책(제안값, 임의): 최근 5쌍 중 가장 최근 1쌍은 원문(상한 약 3000자), 나머지 4쌍은 답변을 Haiku가 약 300자로 축약, 프롬프트는 원문(상한 500자). `추천:` 블록은 항상 원문 전체. 프로그레스 요약 상한 약 1500자(열린 workstream별 목표/다음 행동/에이전트 ID/결과 경로 한 줄씩).
  - 토큰 예산(추정, 미측정): 주입 합계 약 3~5k 토큰/입력(최근 쌍 약 2k + 추천 약 0.3k + 프로그레스 약 0.7k + 고정 지시문). 상주형 평균 컨텍스트 135k~270k 대비 매우 작음. Haiku 증분 요약 호출: 입력 약 3k(직전 요약+방금 턴), 출력 약 0.5k 토큰/턴 [추정], Haiku 단가라 상주형 cache read보다 훨씬 쌈. 답변이 길면 Haiku가 4쌍 축약에 쓰는 입력이 늘지만 한 번 축약한 결과는 재사용(캐시)하므로 턴당 새로 축약하는 것은 방금 밀려난 1쌍뿐.
  - 지연: 증분 요약은 응답 표시 후 백그라운드로 실행해 다음 입력 전에 끝나도록 함(Haiku 호출 수 초 [미측정]). 다음 입력이 요약 완료 전에 오면 이전 요약+방금 턴 원문 일부로 폴백하거나 완료까지 대기(정책 선택 필요). 지휘자 child를 입력마다 새로 띄우는 기동 지연은 별도.
  - 위험: 요약 누적 오차(증분 갱신은 오류가 쌓임, N턴마다 transcript 기반 전체 재생성으로 보정 필요), Haiku의 사실 왜곡, 5쌍 밖 지시어. 미검증.
- 중간안: 15분 무입력 교체(3-2)와 270k 교체(3번)가 이미 상주형과 무상태형의 중간. 무상태형은 4번 실험에 세 번째 조건(Sonnet 상주 / Opus 상주 / Sonnet 무상태)으로 추가해 비용, 정정 반복 횟수, 지시어 해결 실패율을 측정. 채택 기준은 총비용 대비 정정 반복이 상주형 이하일 때. 미검증이므로 결정하지 않음.

## 4-c. 서브에이전트 대신 하네스가 띄우는 멀티 세션 (옵션; 사용자 정정 261028: "아니 서브에이전트를 쓰는 대신 멀티 세션을 사용하는게 어떻냐는 말이지")
- 정정: 이전 4-c(항목별 메인 세션 + 전환 UI)는 의도와 다름. 의도는 Task 서브에이전트 대신, 하네스가 `claude -p` 워커 세션을 직접 띄우고 관리하는 것 [사용자 문구 기반]. 지휘 메인(Sonnet)은 워커에 일을 맡기고 결과 경로를 받음. 이전 4-c의 전환 UI/자동 분류/세션 상태 설계는 폐기(사용자 요청 없음). 사용자 문구의 앞선 인용("여러 메인 세션", "새 클라이언트")은 하네스가 워커 세션을 소유한다는 뜻으로 해석 [추정].
- 구조(제안): 하네스가 워커 레지스트리를 보유. 워커 = 독립 `claude -p` stream-json child(역할별 모델/시스템 프롬프트/도구 제한: 기존 .claude/agents/*.md 내용을 `--append-system-prompt`와 `--allowedTools`/`--model`로 이식). 결과는 워커가 notes/runs/ 파일로 쓰고 하네스가 완료를 감지(3-1의 결과 파일 안정화 + child 종료 이벤트)해 메인의 다음 입력에 `[worker done] ID · task · path`로 주입. 워커는 `--resume <session_id>`로 이어가기(같은 workstream 연속 작업 = 현재 "같은 인스턴스 이어쓰기"에 해당).
- 위임 방식 비교:
  - (A) 하네스 제공 MCP 도구(`delegate(role, task, resume_id?)`, `worker_status`, `worker_result`): 메인이 구조화된 호출을 하므로 파싱 오류 없음, 권한/도구 기록이 transcript에 남음, 메인의 Task 도구는 차단. 구현: 하네스가 stdio/HTTP MCP 서버를 내장하고 `--mcp-config`로 메인 child에 연결 [claude CLI의 MCP 지원은 일반 지식, 이 환경 미검증]. 동기/비동기 반환(즉시 ID 반환 + 완료 알림)을 설계해야 함.
  - (B) 출력 파싱(예: 답변 안의 `@@delegate{...}` 블록): MCP 불필요, 구현 작음. 단점: 모델이 형식을 어기거나 코드블록에 인용만 해도 오탐/누락, 도구 결과를 같은 턴에 돌려줄 수 없어 한 턴 지연. 권고는 A, B는 프로토타입용 [추정].
- 비교(모두 추정/공식 문서 기반, 측정 전):
  - 토큰/시스템 프롬프트: 서브에이전트는 에이전트 정의 프롬프트+도구 설명을 쓰지만 CLAUDE.md/프로젝트 컨텍스트 로딩은 일부 공유·축약됨 [불확실]. 별도 `claude -p` 세션은 매번 완전한 Claude Code 기본 시스템 프롬프트+도구 정의(수 k~수십 k 토큰 [미측정])와 CLAUDE.md, hooks의 SessionStart 주입까지 새로 로드. `--bare`/최소 플래그 및 `--system-prompt` 대체로 줄일 수 있으나 도구 정의는 남음. 워커마다 고정 오버헤드가 서브에이전트보다 클 가능성이 높음.
  - 캐시: cache-ttl.md 기준 구독 내 "메인 대화 1h, 그 외 요청 5m". 서브에이전트는 5m 버킷(`CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`로 조정 가능). 별도 세션의 워커는 자체적으로 "메인 대화"이므로 1h 캐시를 받음(쓰기 2x 단가): 같은 워커를 5분 넘겨 다시 쓰는 `--resume` 패턴에서는 유리, 일회성 워커에서는 2x 쓰기가 손해. TTL은 `CLAUDE_CODE_PROMPT_CACHE_TTL`로 워커별 5m/1h 선택 가능.

### 7-1. 안전장치 미구현인데 최적화만 쌓임
- 원칙: "안전장치 먼저" 게이트. 안전장치 3종(인계 검증, 추천 보존, 270k 전환)이 켜져 있고 검증 통과해야 다른 최적화 플래그(7-2~7-6)를 켤 수 있음. 플래그 상호 의존을 시작 시 검사해 위반이면 경고 후 최적화 플래그를 꺼서 시작.
- 인계 검증(handoff validation): rotate 직후 인계 노트를 로컬 규칙으로 검사. 필수 섹션 7개(목표, 결정, 변경 파일, 진행 중, 열린 질문, 사용자 선호, 정확한 코드/숫자) 존재, 최소 길이, 직전 `추천:` 블록 전문 포함, 변경 파일 목록이 `git status`와 일치. 실패 시 폴백: 인계 노트를 버리고 buildSnapshot(최근 N턴 원문)만으로 시작하며 rotate를 1회 재시도 후 그래도 실패면 rotate 보류(현 세션 유지) + 경고. 모델 호출 없는 검사만 사용.
- 추천 보존: 마지막 답변의 `추천:` 블록을 절단 없이 별도 필드로 저장해 인계 노트와 무관하게 새 세션 첫 입력 앞에 붙임. 검증: 새 세션 첫 메시지에 해당 문자열이 바이트 단위로 포함되는지 비교.
- 270k 전환: 이미 확정된 규칙(매 답변 후 컨텍스트 ≥270k). 구현 순서 맨 앞. 검증은 usage 로그의 input+cache 합계가 270k 도달 턴 직후 rotate 이벤트가 기록되는지.
- 검증 방법: (a) 단위 테스트 - 필수 섹션 누락/추천 누락/파일 불일치 샘플 3종 입력해 폴백 경로 확인, (b) 계측 지표 `handoff_valid`(true/false), `reco_preserved`, `rotate_at_tokens` 집계. 합격선 제안: 실제 사용 20회 rotate에서 handoff_valid ≥95%, reco_preserved 100%.

### 7-2. 세션 워커: 시작 19.6k vs 14.7k, 근거 약함, 복잡도 큼
- 증거 상태: 1회 실행, 프로젝트 밖 측정 [notes/runs/261028-test-worker-vs-subagent.md 기준]. 결정 근거로 부족.
- 단계 도입: 기본 off(`--workers=off`). 1단계는 서브에이전트 유지 + 하네스가 각 위임의 토큰/시간을 로그만 기록(섀도 계측). 2단계는 한 종류 작업(예: 코드 수정)에만 워커 on, 나머지는 서브에이전트. 3단계 확대는 아래 합격선 통과 시에만.
- 복잡도 억제: 워커 수 상한 2, 워커별 타임아웃, 워커 프로세스는 하네스 종료 시 일괄 Kill, MCP/상태 파일은 `notes/workers/<id>.json` 한 곳. 워커 시작 실패/무응답 30초면 즉시 서브에이전트 경로로 폴백(같은 브리프 재사용).
- 검증: 프로젝트 안에서 같은 작업 쌍을 N≥5회씩 반복(서브/워커 교대)해 시작 토큰, 총 토큰(캐시 읽기/쓰기 분리), 벽시계, 성공률 중앙값 비교. 워커 채택 조건 제안: 총 비용 중앙값이 서브에이전트 이하 + 실패율 동일 이하. 미달이면 워커 코드를 플래그 뒤에 두고 확대 중단.

### 7-3. 무상태 지휘자가 1500자 Haiku 요약에 의존 -> 조용한 오분류
- 입력 보강: 요약 길이 상한을 고정 1500자에서 가변(원문 최근 5쌍 전문 + 요약)으로 바꾸고, `추천:`/숫자/경로는 정규식으로 추출해 요약과 별개로 원문 그대로 첨부(Haiku가 못 건드림).
- 탐지: 지휘자 라우팅 결정마다 `route_reason`(한 줄)과 `confidence`(high/low)를 출력하게 하고 기록. 라우팅 후 사용자 교정 신호("아니", "그게 아니라", 같은 항목 재요청)를 휴리스틱으로 잡아 `reroute_suspect`로 기록.
- 폴백: confidence=low이거나 요약에 없는 개체(파일명/숫자)를 지휘자가 인용하면 원문 최근 턴을 추가로 읽는 2차 경로(Sonnet이 원문 직접 읽음) 후 재결정. 해당 경로 비율이 높으면 요약 방식이 부족한 신호.
- 단계: 섀도 모드(무상태 지휘자가 결정만 하고 실제는 현행 경로 실행) -> 결정 불일치율 측정 -> 일치율 합격 시 전환.
- 검증: 과거 transcript 30턴 재생(replay)해 현행 대비 라우팅 일치율, 추천/숫자 누락 건수. 합격선 제안: 일치율 ≥90%, 누락 0건. 불일치는 수동 검토.

### 7-4. EN + Haiku 번역 (지연, 헤지/숫자/형식 충실도)
- 별도 테스트가 진행 중이므로 중복 측정하지 않음. 여기서는 운영 안전장치만.
- 플래그 `--translate=off|on`, 기본 off. 번역 결과에 로컬 검증을 둠: 원문과 번역문의 숫자 토큰 집합 동일, 코드블록/경로/URL 개수와 내용 동일, `추천:` 줄 존재 여부, 길이비 범위. 하나라도 실패하면 번역 폐기하고 원문(영어)을 그대로 보여주는 폴백(또는 사용자 설정에 따라 원문 우선).
- 사용자가 `원문` 입력 시 직전 영어 원문을 보여주는 탈출구. 지표: `translate_ms`, `translate_check_fail` 비율.
- 검증: 별도 테스트 결과를 입력으로 삼고, 운영에서는 check_fail 비율 ≤5%, 추가 지연 중앙값이 정한 상한 이내일 때만 기본 on 후보.

### 7-5. 59:59 캐시 갱신은 1h TTL 가정, overage 감지 미검증
- 감지: 매 응답 usage의 `cache_creation`/`cache_read`를 기록. 갱신 직후 턴에서 cache_read 비율이 낮고 cache_creation이 큼(예: 읽기 < 50%)이면 TTL이 1h가 아닌 것으로 판정하고 `ttl_mismatch` 이벤트 기록. 가능하면 usage.cache_creation의 ephemeral_5m/1h 필드 분리값을 직접 사용 [필드 존재는 미확인, 실제 이벤트 JSON으로 확인 필요].
- 폴백: ttl_mismatch 2회 연속이면 유휴 임계를 4:50으로 자동 강등하고 이후 세션 유지, 경고 표시. overage 상태 신호(rate_limit 이벤트의 overage 표시)가 이벤트에 있으면 사전에 강등 [존재 미확인].
- 안전 마진: 기본 3570s(59:30)로 시작, 3599s는 실측 후에만.
- 검증: (a) 실제 사용 로그에서 5분/30분/58분 무입력 후 cache_read 비율 측정(실제 하네스 사용 중 자연 발생분 우선), (b) 강등 로직은 usage 가짜 이벤트로 단위 테스트.

### 7-6. 답변당 레이어 과다 (Haiku 수집 -> 지휘자 -> 워커 -> Haiku 번역)
- 레이어별 예산: 단계마다 `*_ms`를 기록하고 단계별 타임아웃 후 건너뛰기 폴백(수집 타임아웃이면 직전 요약 재사용, 번역 타임아웃이면 원문 표시).
- 단순 질의 바이패스: 위임이 필요 없는 질의(설명/해석)는 지휘자 단계에서 바로 답하고 수집·워커·번역을 하지 않는 경로. 레이어 수를 로그(`layers_used`).
- 단계적 활성화: 레이어를 하나씩만 추가(현행 -> +수집 -> +무상태 지휘자 -> +번역), 각 단계에서 지연 p50/p90, 실패/폴백율, 비용을 직전 단계와 비교.
- 검증: 지표 `e2e_ms`, `layers_used`, `fallback_count`. 합격선 제안: 단계 추가 시 p90 지연 증가가 정한 상한 이내이고 폴백율 ≤5%. 초과 시 그 레이어는 기본 off.

### 7-7. 테스트 비용: 실제 하네스 사용 로그로 측정
- 별도 합성 실험 대신 7절 공통 계측을 켜서 평소 사용분에서 수집. 플래그 on/off를 세션 단위로 교대(A/B 교대 일자 또는 세션 홀짝)해 같은 사용자 작업에서 비교.
- 분석은 로컬 스크립트(모델 호출 없음)로 `metrics/*.jsonl`을 집계. 필요 표본 크기를 사전에 정함(예: 조건당 ≥20턴). 표본이 모이기 전에는 결론을 내리지 않음.
- 한계: 작업 내용이 달라 비교 노이즈가 큼 [추정]. 보정을 위해 작업 유형 태그(코드/분석/글/실행)를 기록하고 유형별로 비교. 정말 필요한 통제 실험만 소규모로 유지.
- 검증: 계측이 usage 합계를 `/usage`나 사용량 표시와 ±5% 내로 맞추는지 하루치로 대조.

### 7-8. 단계 순서
1. 계측(JSONL) + 플래그 틀. 모델 호출 없음. (7-7, 모든 항목의 전제)
2. 안전장치: 270k 전환, 추천 보존, 인계 검증 + 폴백 (7-1).
3. 캐시 TTL 감지/강등 (7-5): 계측만으로 가능, 59:59 사용 전 필수.
4. 섀도 모드: 무상태 지휘자 결정만 기록, 서브에이전트 위임 토큰 계측 (7-3, 7-2 1단계).
5. 일정 표본 후 판정: 지휘자 일치율, 레이어별 지연. 합격 시 한 레이어씩 on (7-6).
6. 번역은 별도 테스트 결과 + 7-4 검증 장치가 갖춰진 뒤 on 후보.
7. 세션 워커는 마지막, 7-2 합격선 통과 시 한 작업 유형부터.
각 단계 종료 조건은 해당 항목 "검증" 합격선이며 미달이면 다음 단계로 가지 않음.
